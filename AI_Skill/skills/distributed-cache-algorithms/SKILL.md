# 分布式缓存算法

> 覆盖分布式缓存的对象放置与再平衡算法，是水平扩展缓存层的决策基础。

## 1. 概述与适用场景

- **覆盖**：一致性哈希、虚拟节点、Rendezvous（HRW）、变种算法、扩缩容再平衡。
- **适用**：设计缓存分片/路由层；评估扩缩容成本；评审 01.03 文档。
- **不适用**：单节点替换策略（→ cache-algorithms-*）；分布式一致性协议（→ distributed-architecture）。

## 2. 核心要点

1. 一致性哈希（Karger et al., STOC 1997）把节点/对象映射到环，增删节点仅移动相邻弧段数据，期望迁移量 ≈ 1/n（n 为节点数），显著优于取模哈希（全量迁移）。
2. 标准一致性哈希的方差问题：均匀随机放置下节点负载 χ² 分布，热点节点可能 2-3 倍超均值；虚拟节点（每个物理节点 v 个虚拟点，典型 v=100-200）将负载标准差降低约 √v 倍（推导自 Karger 论文分析，B 级）。
3. Rendezvous/HRW（Thaler & Ravishankar, TPDS 1998）无需维护环结构，节点集合变更时全节点独立计算同一归属，天然适合无中心与动态成员场景（如 CacheKit、部分 CDN 调度）；代价是每次查找 O(n)（可用堆/跳表加速）。
4. 倾斜修正手段：虚拟节点、容量加权（按内存/权重设 v）、二次均衡（rebalance）、热点副本（hot key 复制到多节点，见 04.04.04）。
5. 扩缩容工程事实：Facebook memcache（NSDI 2013）用"客户端路由表 + 专用池（Gutter）+ 复制池"应对热点与尾延迟，是生产一致性哈希实践的对照基准。
6. 再平衡与驱逐联动：节点加入后的数据迁移会污染现有缓存（冷缓存效应），应安排在低峰并配合预热（见 02.03.06 云数据库 Heat Map 思路）。

## 3. 权威速查

| 算法 | 结构 | 查找复杂度 | 扩容迁移 | 适用 |
| ---- | ---- | ---------- | -------- | ---- |
| 取模 | 无 | O(1) | 全量 | 固定小集群 |
| 一致性哈希+虚拟节点 | 哈希环+平衡树 | O(log n) | ≈1/n 数据 | 主流（Redis Cluster 槽位是其特例） |
| Rendezvous(HRW) | 无中心 | O(n)→O(log n) 加速 | 最小必要 | 无中心/动态成员 |
| 槽位预分片 | 固定 16384 槽 | O(1) | 槽迁移 | Redis Cluster（固定槽数折中） |

## 5. 常见任务工作流

### 任务 A：设计分片层

1. 确定节点规模与变化频率：稳定大集群→槽位/一致性哈希+虚拟节点；频繁弹性伸缩→Rendezvous。
2. 写入 §3 速查的复杂度与迁移量预算，做扩容演练脚本（参见 cache-operations-testing）。
3. 热点预案：热点副本/Gutter 池/本地多级缓存回退。

### 任务 B：评审分片实现

核对：节点权重是否进入哈希计算；再平衡是否影响驱逐策略稳定性；故障摘除是否引发连锁再平衡（设抖动窗口）。

## 6. 国际前沿对齐（截至 2026-11）

- 一致性哈希仍是默认方案；Rendezvous 在无中心场景（边缘、联邦缓存）热度上升。
- Dragonfly/Garnet 等新兴实现提供替代集群模型对照（见 redis-ecosystem-versions）。
- LLM 前缀缓存的跨节点共享（Mooncake Store、LMCache）把"放置算法"问题引入 KV-block 粒度：按前缀树路由 + 全局索引，成为新研究点。
