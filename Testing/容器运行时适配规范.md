# 容器运行时适配规范（hermes 本地执行的环境抽象层）

> 本地执行环境可能是 **Docker / Podman / K8s（kind/minikube）** 之一。本规范定义：能力探测顺序、命令适配表、用例的运行时要求标注法、以及各运行时的已知差异。hermes 执行任何 L2/L3 用例前必须先按 §1 探测并锁定运行时，再按 §2 适配命令；**不可静默混用**。

## 1. 运行时锁定（2026-11-21 修订：podman 唯一）

```bash
# 探测链（podman 唯一受支持；缺失即 NO_CONTAINER，不做 docker 回退——宿主 docker daemon 长期停用，
# 双轨并存导致命令/网络语义漂移风险（host.docker.internal vs host.containers.internal、pasta 网络等实证差异））
1. podman info  >/dev/null 2>&1              → PODMAN（唯一路径）
2. 其他全部                                   → NO_CONTAINER（L2/L3 全 SKIP，仅跑 L1；登记观察区待用户装 podman）
```

- 版本下限见 `Testing/fixtures/lab.env` `BC_RT_VERSION_MIN`；低于下限=能力缺失按 §4 降级。
- 探测结果记入会话执行记录（执行计划 §3 第 1 步内）。
- 历史 docker 回退链保留在 git 历史；本文档不再维护 docker 列（迁移裁定 2026-11-21：单一运行时降漂移）。

## 2. 命令适配表

| 操作 | Docker | Podman | K8s（kind） |
| ---- | ------ | ------ | ----------- |
| 编排启动 | `docker compose -f <f> up -d` | `podman compose -f <f> up -d`（插件）或 `podman-compose -f <f> up -d` | `kubectl apply -f <manifest目录>/`（fixtures/k8s/，规划中） |
| 环境销毁 | `docker compose -f <f> down -v` | 同左（compose 子命令一致） | `kubectl delete -f <manifest目录>/` |
| 执行命令 | `docker exec <c> <cmd>` | `podman exec <c> <cmd>` | `kubectl exec <pod> -- <cmd>` |
| 日志 | `docker logs <c>` | `podman logs <c>` | `kubectl logs <pod>` |
| 拉镜像 | `docker pull` | `podman pull` | `kind load docker-image <img>`（本地镜像先入 kind） |
| 宿主网关 | `host.docker.internal` | **`host.containers.internal`**（必须改！） | `host.minikube.internal`（minikube）/ 集群内服务名（kind） |
| 构建镜像 | `docker build` | `podman build` | `docker build` + `kind load` |

**fixture 改造责任**：`Testing/fixtures/redis-lab/*.yml` 中 `host.docker.internal` 在 Podman 下必须替换为 `host.containers.internal`——hermes 执行前用 `sed -i` 按运行时切换（执行后还原），或在本地维护一份 `monitoring-compose.podman.yml` 覆盖文件（推荐后者，避免反复改源文件）。

## 3. 用例的运行时要求标注法

每个 L2/L3 用例文件头部统一标注（在"自动化"行后新增一行）：

```markdown
- **运行时**：DOCKER+PODMAN｜K8S（kind）｜ANY（L1 自动化项无需标注）
```

| 标注 | 含义 | 当前用例归属 |
| ---- | ---- | ----------- |
| ANY | 纯脚本/静态检查，无容器依赖 | 全部 L1 项 |
| DOCKER+PODMAN | compose 可表达的环境 | TC-CLUS-001~009（除 008 集群扩容外）、TC-OPS-005-A、TC-BENCH-005 |
| DOCKER（暂） | 依赖 docker 特有行为（host.docker.internal、Desktop 网络） | TC-OPS-005-C（监控全栈，待验证 podman 兼容后升级） |
| K8S（扩展） | 需 K8s 原生能力（Chaos Mesh、Operator） | 剧本 S1-S3 的进阶形态（Docker 版为基本盘）、TC-CLUS-008 的 Operator 化变体（规划） |

**标注维护**：用例新增/改造时同步标注；执行计划 §2 矩阵的"前置"列以标注为准。

## 4. 运行时已知差异与降级规则

| 差异 | 影响 | 降级 |
| ---- | ---- | ---- |
| Podman rootless 端口 | 无（本项目全高位端口 6379+） | — |
| Podman 无 compose 插件 | 编排失败 | 探测时检查 `podman compose version`；无则试 `podman-compose`；都无 → 降级 NO_CONTAINER 跑 L1 + 登记待办 |
| Podman 镜像拉取认证 | ghcr.io 镜像（toxiproxy）不受影响；docker.io 同 Docker 的认证限制 | 同 TC-OPS-005-C 的 docker login 前置 |
| K8s（kind）无 host 网关别名 | exporter 连宿主 Redis 失败 | kind 下 Redis 一并入集群（fixtures/k8s/redis-lab.yaml 规划产物）；监控栈用 NodePort 暴露 |
| K8s 无 docker exec 语义 | 用例命令形态差异 | 用例步骤写成"语义步骤 + 命令示例（Docker 版）"，hermes 按 §2 表自行映射，不逐条重写用例 |
| Windows + Podman（WSL） | 卷挂载路径、网络栈差异 | 首次执行前跑一次冒烟（sentinel 环境 PING）再进正式用例 |

## 5. K8s 化路线（规划，非本轮实现）

1. **短期（已可用）**：kind/minikube 上手工 apply 等价的 Pod/Service manifest——用例标注 K8S（手动），hermes 可按需执行。
2. **中期**：产出 `Testing/fixtures/k8s/`（redis-lab 的 Deployment+Service+监控栈 manifest，由 compose 文件人工翻译并核验），用例步骤补 kubectl 映射。
3. **长期**：Operator 化验证（KubeBlocks 安装 + Redis 集群 CRD，对应 cloud-native-cache 技能 §5 任务 B 的实操版）——入季度剧本。
