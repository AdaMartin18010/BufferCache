## 1. 概述

云数据库（Aurora、PolarDB、Neon、Azure SQL 等）普遍采用**计算-存储分离**架构：计算节点无状态化、数据页放入共享存储/分布式存储层。这一架构颠覆了传统数据库"缓冲池 + 本地磁盘"的两级假设：

- **Miss 不再等于本地磁盘 I/O**：而是从网络存储读取（延迟 100μs-数 ms，且共享带宽）
- **缓存不再私有**：多个计算节点面对同一份数据，缓存状态需要在节点间协调（或接受多副本）
- **节点会消失**：Serverless 缩容到零意味着缓存完全丢失，扩容意味着冷启动

本节分析三个代表性系统的缓存设计及其启示。

## 2. 存算分离架构对缓存的根本改变

| 维度 | 传统单体数据库 | 存算分离云数据库 |
| ---- | -------------- | ---------------- |
| Miss 来源 | 本地磁盘（~1-10ms） | 共享存储网络读（~0.5-5ms，共享带宽） |
| Buffer Pool 所有权 | 实例私有 | 计算节点私有（多节点各持副本） |
| 节点故障 | 缓存随实例重建 | 缓存与计算节点生命周期解耦（可预热迁移） |
| 弹性 | 垂直扩展为主 | 水平扩展 + Serverless 缩零 |
| 一致性 | 单写者 + WAL | 多计算节点 + 存储层仲裁/版本链 |

缓存设计的三个新问题：**Miss 成本上升**（需要更大缓冲池与更聪明的预取）、**多节点缓存冗余**（同页多副本浪费但换取局部性）、**弹性场景的缓存连续性**（预热/迁移机制）。

## 3. Amazon Aurora

### 3.1 存储层与页面缓存

Aurora 把存储层下沉为跨 AZ 的分布式页面服务（page server 逻辑），计算节点维护**本地缓冲池（Buffer Cache）**与一致性视图：

- 计算节点的 buffer cache 缓存数据页 + undo 页，按最近一致 LSN 裁剪旧版本页
- **存储层同时承担"冷缓存"角色**：缓冲池 miss 时从 6 副本存储卷并行读取（quorum 4/6），网络路径替代本地磁盘路径
- 写路径：计算节点只写 redo log（WAL）到存储层，存储层物化页面——**buffer cache 是计算节点唯一的"热数据"层**，写穿压力从数据页转移到日志页

### 3.2 Buffer Pool 预热

Aurora 提供 **缓冲池预热（Buffer Pool Warmup）**：

- 定期把 buffer pool 的页码清单（heat map）持久化到存储层
- 故障转移 / 实例重启 / Serverless 扩容时，按 heat map 优先把热页拉回 buffer pool，避免"冷启动雪崩"
- 这是"缓存状态与计算节点生命周期解耦"的经典实现——对应 [02.04 现代内核缓存机制](../02.04-现代内核缓存机制/README.md) 中"缓存状态外置"的主题

### 3.3 缓存一致性模型

Aurora 计算节点间不直接共享 buffer cache；同一数据页可被多个只读副本缓存：

- 缓存页按 LSN 版本化，读取时与存储层仲裁保证不读到过期页
- 写入者通过存储层广播失效（读后失效而非缓存同步）——**"共享存储 + 私有缓存 + 版本仲裁"**成为云数据库缓存一致性的事实模式

## 4. PolarDB

### 4.1 共享存储与本地缓冲池

PolarDB（阿里云）架构与 Aurora 同族：PolarFS 分布式共享存储 + 一写多读计算节点：

- RW 节点与 RO 节点各自维护本地 Buffer Pool，PolarFS 提供块级共享访问
- RO 节点的缓存页合法性通过全局最小 visible LSN 保障（避免读到未固化页）
- 与传统主备的最大差异：**RO 节点扩容无需数据复制**（共享存储即数据），冷启动时间从小时级降到分钟级，但缓存仍冷——预热机制同样关键

### 4.2 共享内存池

PolarDB 推出**共享内存池（Shared Buffer Pool）**能力：多个计算节点通过 RDMA 共享同一片内存缓存区，避免多节点缓存冗余：

- 页帧全局唯一，节点间通过 RDMA 单边读写
- 命中远程共享缓存的延迟（~2-5μs）远低于存储层读取（~ms 级）
- 这是 **Far Memory 思想（见 [02.04.01](../02.04-现代内核缓存机制/02.04.01-新存储栈缓存技术.md) §6）在数据库缓冲池上的直接落地**——"本地 DRAM → 共享内存池 → 共享存储"三级结构

## 5. Neon：Serverless PostgreSQL 缓存架构

Neon（开源 Serverless Postgres）把存算分离推向极致：

```text
计算节点（无状态，可缩零）
  └── 本地缓存（页缓存 + 预取缓存，DRAM + 本地 SSD）
存储层
  ├── Pageserver：页面版本链 + 分层存储（内存 → 本地 SSD → S3）
  └── Safekeeper：WAL 持久化仲裁
```

- **Pageserver 自身是缓存层次系统**：热页驻留内存、温页在本地 SSD、冷页在 S3，按访问热度在层间迁移——与 [02.04](../02.04-现代内核缓存机制/README.md) 的内存分层主题同构
- **计算节点缓存分层**：DRAM 页缓存 + **本地 SSD 预取缓存**（Neon 的 file cache）：miss 后从 Pageserver 拉页时顺带预取相邻页，SSD 缓存使重复访问不必再跨网络
- **缩零与恢复**：计算节点完全无状态，重启后缓存冷启动；Pageserver 的热度统计可指导预取
- 代表了"缓存下沉到存储层 + 计算层轻量缓存"的云原生路线

## 6. 云数据库缓存的通用设计模式

### 6.1 分层缓存结构

```text
计算节点:  Buffer Pool (DRAM) → 本地 SSD 缓存(可选)
              ↓ miss
共享内存层:  RDMA 共享缓存池(可选, PolarDB式)
              ↓ miss
存储层:      Pageserver 内存 → Pageserver 本地 SSD → 对象存储(S3)
```

每一层是下一层的缓存，层间准入/驱逐按**延迟账**（[04.03.15](../../04-架构设计/04.03-行业应用场景/04.03.15-大模型推理缓存架构.md) §8.4 的同一判据）决策：$t_{reload} < t_{reprefill}$ 的层级才有存在价值。

### 6.2 Miss 惩罚与预热策略

- **Heat Map 持久化**：缓冲池页码清单随实例/存储状态保存，故障转移与扩容时预热
- **优先拉取 redo/undo 页**：恢复路径的页优先进入缓冲池
- **存储层热度反馈**：Pageserver 记录页访问统计，计算节点 miss 时返回"邻近热页"提示（协同预取）
- **读副本亲和**：会话路由到持有其热页的副本（cache-aware routing，与 [04.03.15](../../04-架构设计/04.03-行业应用场景/04.03.15-大模型推理缓存架构.md) 的 SGLang Router 思想相同）

### 6.3 计算节点弹性与缓存状态

| 场景 | 缓存策略 |
| ---- | -------- |
| Serverless 缩容到零 | 接受全冷；恢复时依赖 heat map 预热 + 存储层缓存兜底 |
| 只读副本扩容 | 共享存储免数据复制；缓存按需预热（分钟级可用） |
| 故障转移 | RW 切换；新主预热优先级最高的事务页 |
| 节点池化（多租户） | 节点间缓存互不影响；调度考虑缓存亲和性 |

## 7. 与传统数据库缓存的对比

| 维度 | 传统（[02.03 数据库缓存](../02.03-数据库缓存/) 所述） | 云数据库（本节） |
| ---- | ------------------------------------------------------ | ----------------- |
| 缓冲池形态 | 单实例私有 | 节点私有 + 可选共享池 |
| Miss 惩罚 | 本地磁盘 I/O | 网络存储 I/O（共享带宽） |
| 预热 | 重启后冷启动为主 | Heat Map / 存储层热度引导 |
| 多节点缓存 | 主备各一份（复制延迟） | 共享存储免复制，缓存多副本 |
| 缓存与弹性 | 强耦合实例生命周期 | 解耦（状态外置） |
| 新机制 | Double Write、Change Buffer | 版本化页、RDMA 共享池、分层 Pageserver |
