## 1. PG 18 缓存相关增强（事实层）

| 特性 | 内容 | 缓存意义 | 出处 |
| ---- | ---- | -------- | ---- |
| **异步 I/O（AIO）** | 新 I/O 子系统，批量提交/完成（此前依赖预取与 worker 池模拟） | 缓冲未命中后的回读延迟显著下降，缓存穿透成本降低 | [PG 18.0 Release Notes](https://www.postgresql.org/docs/release/18.0/) |
| **pg_buffercache 逐出接口** | 扩展提供底层逐出指定缓冲的能力（"a low-level way to evict"） | 缓存管理从"只读观测"到"可干预"——外部预热/清缓存可行 | [pg_buffercache 文档](https://www.postgresql.org/docs/current/pgbuffercache.html) |
| **ANALYZE 默认 BUFFERS** | 查询分析默认带缓冲访问统计 | 开发期缓存命中率可见性零成本 | [Bytebase: What's New in PG 18](https://www.bytebase.com/blog/what-is-new-in-postgres-18/)（2026-04） |
| pg_upgrade 保留统计 | 大版本升级不再丢失优化器统计 | 升级后缓存相关计划不抖动 | 同上 |
| UNLOGGED 表（既有） | 不写 WAL 的表，崩溃即清，写入 ~13% 优于常规表 | "PG 作缓存"的载体：unlogged + jsonb = KV 缓存 | [freeCodeCamp 2026-04](https://www.freecodecamp.org/news/how-to-use-postgresql-as-a-cache-queue-and-search-engine/) |

## 2. 国际评估："PG 作缓存"的论据

### 2.1 支持论据（"很多时候不需要 Redis"）

1. **组件减法**：单节点场景下 unlogged table + jsonb 就是可用 KV 缓存，"removes a [component]"（Redisson PRO, 2026-08）——少一个组件=少一套HA/监控/备份。
2. **延迟足够好**：非亚毫秒硬需求时 PG 缓存命中延迟（共享内存命中 ~10-100μs 量级）可接受（freeCodeCamp 2026-04："if sub-millisecond latency is not a hard requirement"）。
3. **2026 生态大势**："PostgreSQL is the good enough option for almost every database category"（LabHub 2026-05，向量/时序/搜索均有扩展方案）——缓存是这一趋势的延伸。
4. **运维一致性**：缓存与数据同引擎——备份/权限/复制统一，无缓存-DB 双运维面（[PgCache 2026-09](https://www.pgcache.com/blog/postgresql-caching/)）。

### 2.2 反对论据（"Redis 仍不可替代的场景"）

1. **延迟差距不可否认**："Redis is faster than postgres when it comes to caching, there's no doubt about it"（dizzy.zone 2025-09）——PG 赢在简化不是性能。
2. **数据结构丰富度**：zset/geo/Streams/位图等专用结构 + 成熟原子操作，PG jsonb 模拟需应用层补齐。
3. **TTL 管理**：PG 无原生 TTL（需 pg_cron 或 TTL 列+定时清理），Redis 过期是内建一等公民。
4. **消息与锁**：pub/sub、 Streams 消费组、分布式锁（Redlock 争议但生态成熟）——PG LISTEN/NOTIFY 是轻量通知非消息队列（[04.03.19](../../04-架构设计/04.03-行业应用场景/04.03.19-Redis-Streams与消息队列边界.md) 的边界同样适用）。
5. **共享缓存拓扑**：多应用共享缓存时 PG 是重库（连接成本），Redis 是轻缓存（专用协议+客户端生态）。

### 2.3 国际评估的共识形态

各方评估收敛于"**先评估 PG 内嵌缓存，不够再加 Redis**"（PG-first 策略）：新项目默认 PG unlogged 缓存起步，出现以下任一信号再引入外部缓存：QPS/延迟 SLO 突破、需要专用数据结构、跨应用共享、TTL 精细需求。这与本项目 [04.03.16 §6 决策树](../../04-架构设计/04.03-行业应用场景/04.03.16-云原生缓存趋势与实践.md) 的"应用内缓存（L3）优先"层级一致。

## 3. 边界决策树

```text
需要缓存层？
├─ 单实例部署 + 非亚毫秒 SLO + 数据可回源 + TTL 分钟级可容忍
│   → 【PG 内嵌缓存】unlogged 缓存表（jsonb 值 + TTL 列 + pg_cron 清理）
│     （判定指纹 F19-a；出处本节 §2.1）
├─ 需专用数据结构（zset/geo/位图/Streams）？
│   ├─ 是 → Redis（数据结构是硬需求）
│   └─ 否 → 继续
├─ QPS > 数万或延迟 P99 < 1ms 硬 SLO？
│   ├─ 是 → Redis/专用缓存（PG 单连接进程模型是天花板）
│   └─ 否 → PG 内嵌缓存 + pg_buffercache 观测
├─ 多应用共享缓存 / 微服务边界 crossing？
│   ├─ 是 → Redis（共享拓扑 + 连接轻量）
│   └─ 否 → PG 内嵌
└─ TTL 秒级精度 / 自动过期强需求？
    ├─ 是 → Redis（内建惰性+定期过期，03.04.06 机制）
    └─ 否 → PG 内嵌（pg_cron 分钟级清理可容忍时）
```

**PG 内嵌缓存的工程要点**（投影层，权威判定在本节）：

- 载体：UNLOGGED 表（崩溃即清 = 缓存语义天然匹配，无需持久化恢复）；
- 失效：TTL 列 + pg_cron 周期删除，或应用层懒过期（读时判 TTL）；
- 观测：`pg_buffercache` 看 shared_buffers 命中 + `EXPLAIN (ANALYZE, BUFFERS)` 默认带缓冲统计（18 起零成本）；
- 驱逐干预：18 起 pg_buffercache 提供 evict 接口，预热/清缓存可脚本化；
- 上限：shared_buffers 命中是主路径，OS 页缓存（[02.01.01](../02.01-操作系统缓存/02.01.01-Linux-Page-Cache机制.md)）是二级——双缓存账按 02.03.03 口径核算。

## 4. 混合架构模式

渐进路径（与 [04.03.19 §5 迁移路径](../../04-架构设计/04.03-行业应用场景/04.03.19-Redis-Streams与消息队列边界.md) 同构）：

1. **起步**：PG unlogged 缓存表（单组件）。
2. **信号触发**（§3 决策树任一"是"）：引入 Redis，缓存从 PG 表迁移（应用双读过渡 + [04.04.11 对账](../../04-架构设计/04.04-缓存问题与治理/04.04.11-缓存数据对账与校验.md)）。
3. **分工**：热点/结构化数据在 Redis，会话/可回源 KV 留 PG——避免"所有缓存一刀切迁移"。
4. **反向路径**：Redis 集群收缩时，可回源数据回落 PG unlogged（组件减法收益回收）。

## 5. 判定指纹与一致性

| 指纹 | 结论 | 本节锚点 |
| ---- | ---- | -------- |
| F19-a | 单实例+非亚毫秒+可回源+TTL分钟级 → PG unlogged 缓存表 | §3 决策树根 |
| F19-b | 需 zset/geo/Streams 等专用结构 → Redis | §3 第二问 |
| F19-c | QPS>数万或 P99<1ms 硬 SLO → Redis | §3 第三问 |
| F19-d | 多应用共享缓存 → Redis | §3 第四问 |
