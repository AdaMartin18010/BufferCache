# 02.03.09 缓存-数据库光谱与内存数据库

> Garnet 论文的实证（[03.05.01 §4.7](../../03-Redis组件/03.05-Redis生态与版本演进/03.05.01-开源缓存技术全景图.md)）："70%+ Redis 用户把 Redis 当数据库用"。本文把分散的"缓存"与"数据库"两篇体系收敛为一条**光谱**：从纯缓存到内存数据库，中间是连续的持久性/一致性设计空间。判定指纹 F26 已入册。

## 1. 光谱七档

| 档 | 系统形态 | 持久性 | 典型 | 适用 |
| -- | -------- | ------ | ---- | ---- |
| S1 纯缓存 | 无持久化，全可重建 | 无 | Redis noeviction 关闭持久化 | 任意回源 |
| S2 可重建+兜底 | RDB 快照（低频） | 分钟级 RPO | Redis RDB-only | 回源expensive但可容忍分钟丢失 |
| S3 可恢复缓存 | AOF everysec + 混合 | 秒级 RPO | Redis/Valkey 生产默认 | [03.02.06 §4](../../03-Redis组件/03.02-持久化机制/03.02.06-持久化策略全局决策与成本模型.md) |
| S4 强持久缓存 | AOF always / 可调持久性（Garnet DOL 分层提交） | ~零 RPO | Garnet（SSD+云双提交） | 缓存即真相源过渡 |
| S5 内存数据库 | 内存主存储 + 持久化日志/快照 + SQL | 事务级 | SingleStore（行存内存+列存磁盘）、VoltDB | 数据量内存可容纳、低延迟事务 |
| S6 分布式内存 SQL | 水平分片 + 标准 SQL | 事务+复制 | SingleStore 分布式 / Apache Ignite SQL | 分析+事务混合 |
| S7 新形态 | 存算分离内存层 | 对象存储兜底 | Neon/Aurora 的缓冲池中心架构（[02.03.6](../02.03-数据库缓存/02.03.06-云数据库缓存架构.md)） | 云原生数据面 |

**光谱的设计含义**：①"缓存还是数据库"不是二选一而是**选档**——依据是 RPO/RTO/查询复杂度/数据量四条判据（§3）；②档位上移的代价单调递增（持久化 IO/复制协议/事务），收益是少一个组件与更低延迟；③**S4 是 2026 的新活跃区**——Garnet 的"可调持久性"（ephemeral→checkpoint→lazy→full 四模式）让同一系统沿光谱滑动，这是对"选档"问题的产品化回答。

## 2. 内存数据库的本质差异

| 维度 | 缓存（S1-S4） | 内存数据库（S5-S6） |
| ---- | ------------- | ------------------- |
| 数据模型 | 键值+结构 | 关系+SQL（优化器） |
| 一致性 | 最终一致为主 | ACID 事务 |
| 查询能力 | 点查+结构操作 | 任意 SQL（索引/ join） |
| 容量假设 | 工作集内存 | 全量内存（或内存+磁盘分层） |
| 失败语义 | 缓存失效=性能事件 | 持久化=正确性事件 |

**SingleStore 要点**（C 级，官网交叉核验 2026-11）：内存行存（低延迟 OLTP）+ 磁盘列存（分析）双引擎统一 SQL；标准 MySQL 协议——缓存升级路径平滑。

## 3. 选档判据（F26）

| 指纹 | 判据 | 档位 |
| ---- | ---- | ---- |
| F26-a | 全量可回源+丢失可容忍 → S1-S2 | 纯缓存 |
| F26-b | 回源 expensive+秒级 RPO 可容忍 → S3 | 生产缓存默认档 |
| F26-c | "缓存即真相源"倾向+要写保护 → S4（评估 Garnet 式可调持久性） | 2026 活跃区 |
| F26-d | 需要事务/SQL/容量超内存 → S5-S6 | 内存数据库 |
| F26-e | 云原生+存算分离 → S7 | 缓冲池中心 |

**反模式**：用 S3 缓存+应用双写模拟 S5 的事务——双写不一致窗口+无回滚+无隔离，是光谱上最昂贵的错误位置（不如直接升档）。
