# 02.04.02 数据湖缓存架构

> 云原生数据面的最大缓存场景：计算引擎（Spark/Trino/Presto）与对象存储（S3）之间的高速缓存层。本文梳理两大开源体系 Alluxio 与 JuiceFS 的架构差异、缓存机制与选型，补 [02.04.01 新存储栈](02.04.01-新存储栈缓存技术.md) 的应用层视角。

## 1. 问题与位置

```text
Spark/Trino/AI 训练（计算层）
   ↓ 数据访问（原始：S3 高延迟 ~50-150ms 首字节、无 list 性能）
缓存层（本文：数据本地化 + 元数据加速）
   ↓
对象存储 S3/OSS（存储层，[05.01.6 §2.1](../../05-全栈分析/05.01-硬件层深度剖析/05.01.06-缓存系统三层结构与全链路Metric.md) 全球级延迟）
```

数据湖缓存的两个加速对象：**数据块**（读缓存）与**元数据**（list/stat 操作放大——小文件场景元数据可占 80% 请求量，C 级经验）。

## 2. Alluxio vs JuiceFS（架构对照）

| 维度 | Alluxio | JuiceFS |
| ---- | ------- | ------- |
| 定位 | **分布式缓存层**（加速既有存储，不改数据路径） | **完整分布式文件系统**（元数据+数据分离构建） |
| 架构 | Master/Worker/Client 三组件（[官方对比](https://juicefs.com/docs/community/comparison/juicefs_vs_alluxio/)） | 元数据引擎（Redis/Postgres/MySQL）+ 对象存储 + 客户端 |
| 缓存机制 | Worker 本地缓存 + 分层（MEM/SSD/HDD）+ 异步写 | 客户端本地缓存（内存/磁盘）+ 全局元数据 |
| 一致性 | 缓存语义（最终一致，TTL/同步） | POSIX 强一致（元数据在 DB） |
| 小文件 | 一般（缓存层语义） | **强**（元数据走 Redis ~ms，数据在对象存储） |
| 典型场景 | 大数据分析加速、AI 训练数据本地化 | 海量小文件、共享文件系统、K8s 共享存储 |

（来源：JuiceFS 官方架构对比 2026-07/08，B 级；faun.dev 2026，C 级）

## 3. 缓存机制要点

| 机制 | 说明 | 出处 |
| ---- | ---- | ---- |
| 数据本地化 | 计算任务调度到持有缓存块的 Worker（Alluxio 的 locality 调度） | Alluxio 文档 |
| 短路读 | 同机客户端绕过网络直读 Worker 内存 | Alluxio/JuiceFS 均支持 |
| 分层缓存 | MEM→SSD→HDD 三级（05.01.6 链路账的实例化） | 两者 |
| 元数据缓存 | JuiceFS 客户端缓存元数据（TTL 可调）；Alluxio 的 master 缓存命名空间 | 文档 |
| 写策略 | ASYNC_THROUGH（缓存+异步落对象存储）/ MUST_CACHE / CACHE_THROUGH | Alluxio 写类型 |

## 4. 选型指纹

| 指纹 | 结论 | 锚点 |
| ---- | ---- | ---- |
| F27-a | 已有 HDFS/S3 数据+Spark 加速 → Alluxio（非侵入缓存层） | §2 表 |
| F27-b | 海量小文件/POSIX 语义/K8s 共享卷 → JuiceFS（元数据架构优势） | §2 表 |
| F27-c | AI 训练数据本地化（GPU 直读）→ 两者均可；GPU 直读叠加 GPUDirect Storage（[02.03.8 §4](../02.03-数据库缓存/02.03.08-数据访问中心设计与PG18解剖.md)） | 组合 |

## 5. 前沿（截至 2026-11）

- 湖仓一体（Iceberg/Delta 表格式）使缓存层面向"表级/分区级"预取（而非文件级）——缓存键的语义上移。
- AI 训练场景的缓存与 [04.03.17 LLM 数据通路](../../04-架构设计/04.03-行业应用场景/04.03.17-大模型推理缓存部署实践.md) 汇聚：数据集 staging + KV 缓存共用分层基础设施。
