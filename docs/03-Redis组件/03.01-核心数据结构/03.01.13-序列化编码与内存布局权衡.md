## 1. 概述：三角权衡

序列化格式在三个相互竞争的维度间取舍：

```text
        CPU 编解码耗时
           /        \
          /          \
   网络带宽 ———————— 内存占用
```

- **文本格式**（JSON/XML）：人可读、跨语言零成本，但体积大（key 名重复）、解析慢。
- **二进制 schema**（protobuf/MessagePack）：体积小、解析快，但需 schema 管理与版本兼容。
- **压缩**（zstd/snappy/brotli）：进一步压体积，以 CPU 换带宽/内存，有最小有效长度（小 value 压缩反而膨胀）。

## 2. 格式定量对比

以 1KB JSON 典型对象（含嵌套与 10 个字段）为基准的相对量级（C 级经验值，声明假设：现代 x86、单线程、热数据；具体数字必须自家基准复测）：

| 格式 | 体积（相对 JSON） | 序列化耗时（相对 JSON=1） | schema 管理 | 可读性 |
| ---- | ---------------- | ------------------------ | ----------- | ------ |
| JSON | 1.0 | 1.0 | 无 | 原生 |
| MessagePack | 0.6-0.8 | 0.4-0.6 | 无（自描述） | 需工具 |
| protobuf | 0.4-0.6 | 0.2-0.4 | .proto + 版本规则 | 无 |
| JSON+zstd | 0.15-0.3 | 1.5-3（含压缩） | 无 | 压缩后无 |
| protobuf+zstd | 0.1-0.2 | 1.0-2 | 有 | 无 |

**带宽账**（推导自体积比，B 级）：QPS 10 万、平均 value 1KB JSON → protobuf 后 0.5KB，网卡输出从 ~800Mbps 降到 ~400Mbps（含协议头）；**命中内存带宽账**：同数据量内存占用减半 → 同内存可缓存 key 数近翻倍（[07.05.04](../../07-运维与部署/07.05-集群管理/07.05.04-集群容量规划.md) 公式的 value 项直接受益）。

## 3. 压缩的插入点

| 插入点 | 机制 | 适用 |
| ------ | ---- | ---- |
| 客户端序列化时压缩 | value 存压缩字节 | 大 value（>4KB）且 CPU 富余 |
| Redis 端透明压缩 | 无原生支持；模块/代理层可做 | 需客户端无感 |
| 网络层压缩 | 专用协议/代理（如配备） | 跨 AZ 流量费敏感 |

**最小有效长度**：zstd 对小输入（<100B）输出反而大于输入（帧头开销 ~10-20B，C 级实测）；snappy 帧开销更小。小 value 对象（<1KB）压缩收益常被 CPU 代价抵消——**压缩决策按 value 大小分档**。

## 4. 与 Redis 内部编码的联动

序列化字节流是 Redis 的 value 载荷，与内部编码叠加：

| 内部编码 | 触发条件（8.x 默认） | 与序列化的交互 |
| -------- | ------------------- | -------------- |
| embstr | value ≤44B | 小对象（如压缩后 ID/短状态）最优；JSON 最小值常超阈值变 raw |
| raw/SDS | >44B | 二进制安全承载任意序列化字节 |
| listpack（hash/zset） | 字段/value 均 <64B 且 entries<128 | **序列化格式影响编码**：JSON 字段值易超 64B → 提前升级 hashtable，内存涨 3-5 倍 |

**工程要点**：选择紧凑序列化（字段短名/MessagePack）可使 hash/zset 小对象留在 listpack 编码——内部编码红利与外部格式选择存在乘法效应。

## 5. 决策树

```text
value 平均大小？
├─ <1KB → 可读性优先：JSON 或 MessagePack；不压缩
├─ 1-16KB → CPU 余量？
│   ├─ 足 → protobuf + 可选 zstd（>4KB 部分）
│   └─ 紧 → MessagePack（免 schema 管理）
└─ >16KB → 必压缩（zstd level 3）或拆分对象；评估是否该用对象存储+缓存元数据
跨语言要求强？
└─ 是 → protobuf/Avro（schema 注册表）；否 → 按上
```

## 6. 场景

1. **微服务会话**：JWT/JSON <1KB，不压缩；CPU 留给业务。
2. **商品详情**：protobuf 1-4KB + zstd；详情读多写少，CPU 代价摊薄。
3. **模型特征缓存**：numpy 二进制 + 自定义头；避免 JSON 数值膨胀 3-5 倍。
