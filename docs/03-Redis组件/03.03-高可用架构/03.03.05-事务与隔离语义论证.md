## 1. 概述：三种"事务"形态

| 形态 | 原子性来源 | 回滚 | 隔离性 | 典型用途 |
| ---- | ---------- | ---- | ------ | -------- |
| MULTI/EXEC | 命令排队 + EXEC 一次性执行 | **不支持**（运行时错误不中止队列） | 执行期不被其他命令插入 | 批量原子操作 |
| WATCH+MULTI+EXEC | EXEC 前校验 watched key 版本 | 通过 EXEC 放弃实现"条件失败" | CAS 乐观锁 | 读-改-写竞争 |
| Lua（EVAL/EVALSHA） | 脚本执行期间不插入其他命令 | 脚本内可返回错误但已执行的写不撤销 | 最强（执行期独占） | 复杂原子逻辑 |

## 2. MULTI/EXEC 的语义边界

### 2.1 排队与执行的两阶段

```text
客户端 A: MULTI → SET k1 v1 → SET k2 v2 → EXEC
                ↓（排队期间其他客户端命令正常执行）
服务器:   收到 EXEC → 原子执行队列（不被打断）
```

**原子性边界**：EXEC 执行的命令序列对外不可见中间状态（隔离性的执行期部分），但**队列中的写命令不会回滚**：

- 队列期错误（如 SET 参数错）：命令不入队，EXEC 直接报错，队列清空——安全。
- **执行期错误**（如对 string 做 LPUSH）：Redis 继续执行队列剩余命令（官方设计决策：不回滚，因为运行时错误由程序员 bug 导致而非并发冲突——Redis 事务设计说明，B 级）。

### 2.2 不隔离排队期

MULTI 后的命令只是入队（返回 QUEUED），**其他客户端在 EXEC 前的任何时刻都能修改这些 key**——所以"读-改-写"必须配 WATCH，否则读到的是过期的基础值。

## 3. WATCH 乐观锁的版本机制

WATCH 的实现：被监控 key 维护**修改版本号**（数据库级 dirty 版本递增），EXEC 时比对版本，任一 key 被第三方修改则 EXEC 返回空（全部放弃）。

```text
WATCH stock
val = GET stock          # 读
MULTI
SET stock val-1          # 基于 val 的写
EXEC                     # 若 stock 在 WATCH 后被改 → 返回空，客户端重试
```

- **冲突率决定性能**：高竞争下重试风暴（与 [04.04.08 §3](../../04-架构设计/04.04-缓存问题与治理/04.04.08-缓存失效传播与一致性链路.md) 的失效风暴同构：重试并发 × 冲突概率的放大）。
- **WATCH 与 ABA**：版本号机制天然防御 ABA（不是值比对而是修改计数比对）——比"读值-比对-写"的值比对更强。
- **失效语义**：WATCH 在 key 被**任何修改**（含 EXPIRE、DEL、自己 touch）后失效，粒度粗但实现便宜。

## 4. Lua 脚本的原子性

- **执行期独占**：Redis 单线程执行整个 Lua 脚本，期间不处理其他命令——脚本即"事务"。
- **不撤销**：脚本内 `redis.call` 的写已执行后若脚本后续逻辑出错，已写不回滚（与 MULTI 同原则）。
- **与 MULTI 的选择**：逻辑含条件分支/循环/计算 → Lua；简单批量 → MULTI；需读结果决定后续 → Lua（MULTI 无法读中间结果，GET 在队列中不返回实际值）。
- **复制注意**：Lua 通过 effects 复制（8.x），脚本内非确定性（RANDOMKEY/时间）以执行结果为准复制到从库（官方 replication 文档，B 级）。

## 5. 与 ACID 的对照

| ACID 属性 | Redis 满足度 | 依据 |
| --------- | ------------ | ---- |
| 原子性 A | **部分**：执行期原子，无回滚 | 运行时错误继续执行（官方设计说明） |
| 一致性 C | 部分：语法错误排队失败；数据一致性由应用保证 | 无约束/触发器 |
| 隔离性 I | 执行期隔离（不被插入）；排队期不隔离 | 单线程模型 |
| 持久性 D | **取决于配置**：无持久化=全不满足；AOF always=接近 | [03.02.06](../03.02-持久化机制/03.02.06-持久化策略全局决策与成本模型.md) |

**推论**：需要严格事务语义（资金转移）时不应依赖 Redis 事务——用 [08.02.02 TCC](../../08-分布式架构/08.02-分布式事务/08.02.02-TCC补偿事务实践.md) 或 DB 事务，缓存只承担读取加速。

## 6. 选型决策

| 需求 | 选择 | 理由 |
| ---- | ---- | ---- |
| 批量写原子可见 | MULTI/EXEC | 最简 |
| 读-改-写竞争（库存扣减单 key） | WATCH+MULTI 或 Lua | CAS；冲突率 >10% 时 Lua 重试成本更低（无 WATCH 失效重试，脚本内循环重试） |
| 跨 key 条件逻辑 | Lua | MULTI 无分支能力 |
| 跨分片原子 | **不可用**（Cluster 不支持多 key 事务） | 应用层 Saga/幂等（[08.02.03](../../08-分布式架构/08.02-分布式事务/08.02.03-Saga长事务实践.md)） |
