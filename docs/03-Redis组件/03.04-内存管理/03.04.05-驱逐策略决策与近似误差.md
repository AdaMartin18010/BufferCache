## 1. 八策略分类与选择模型

两个正交维度：**候选集**（allkeys 全部 key / volatile 仅设 TTL 的 key）× **牺牲规则**（lru / lfu / random / ttl-最小）。

**决策树**（推导自策略语义，B 级）：

```text
未设 TTL 的 key 是否允许驱逐（可回源）？
├─ 否 → noeviction（写失败）或 volatile-* + 显式 TTL（推荐后者）
└─ 是 → 访问模式有强热点（少量 key 承载大量访问）？
    ├─ 是 → allkeys-lfu（频率记忆抗扫描）
    └─ 否/扫描混合 → allkeys-lru（时间局部性）
        └─ 需要利用 TTL 信息（业务分层过期）→ volatile-ttl
```

| 策略 | 语义 | 致命误用 |
| ---- | ---- | -------- |
| noeviction | 写超限直接报错 | 当队列用（应 noeviction 是刻意的；误用是没配置策略默认 noeviction 导致写失败"莫名"） |
| allkeys-random | 随机驱逐 | 无（简单均匀；命中率最差之一） |
| allkeys-lru | 最近最少使用 | 扫描负载下误伤热点（扫描项变"最近使用"） |
| allkeys-lfu | 最不常用 | 频率衰减期（lfu-decay-time）配置不当导致新旧失衡 |
| volatile-lru/lfu/random | 仅带 TTL 者 | **key 忘设 TTL → 永不驱逐 → 写失败**（最常见事故） |
| volatile-ttl | TTL 最短者优先 | 与业务 TTL 语义混淆（它按剩余寿命驱逐，非"业务优先级"） |

## 2. 采样驱逐的近似误差

Redis 不维护全局精确 LRU/LFU 序，驱逐时**随机采样 maxmemory-samples 个（默认 5）取最久未使用**（近似 LRU，官方设计文档，B 级）：

- **近似质量 vs 采样数**：采样 5 时在 Zipf 访问分布下近似比（近似 LRU 命中率 / 精确 LRU）官方实测 >95%（Redis 官方 benchmark 口径，B 级；更严格分布下下降，C 级提示）。
- **LFU 更省采样**：对数计数直接可比（不必采样），maxmemory-samples 对 LFU 的影响小于 LRU（05.05.02 计数机制）。
- **调参方向**：命中率敏感且 key 量大 → 采样数升到 10（官方建议的上限平衡点，再升收益递减且 CPU 增）。

## 3. 驱逐路径的成本

驱逐发生在**每次写命令的处理路径**（先检查内存再决定是否驱逐）：

- 单 key 写：判断 + 采样 + 删除 = O(samples) 固定小常数。
- 批量写（MSET 100 key）：每 key 都触发检查，驱逐集中爆发时毛刺。
- **与 activedefrag 叠加**：内存碎片整理（搬运分配块）与驱逐并发时 CPU 竞争（[03.04.02](../../03-Redis组件/03.04-内存管理/03.04.02-内存碎片整理.md) 联动）；观测 `evicted_keys` 速率与 `active-defrag` 指标的时序相关性。

## 4. 策略与业务语义匹配矩阵

| 业务类型 | 推荐策略 | 理由 |
| -------- | -------- | ---- |
| 纯缓存（可回源） | allkeys-lfu | 热点保护最强 |
| 缓存+队列混合 | volatile-lru + 队列显式 TTL | 队列 key 受保护性驱逐 |
| 会话 | allkeys-lru + 会话 TTL | 近似 LRU 够；TTL 兜底 |
| 速率限制计数器 | noeviction | 计数器不可驱逐（否则限流失效） |

## 5. 场景

1. **命中率突降排查**：先查 maxmemory 是否触顶 + 当前策略 + evicted_keys 速率曲线（[04.04.07 指标体系](../../04-架构设计/04.04-缓存问题与治理/04.04.07-缓存监控指标体系.md)）。
2. **扫描任务污染缓存**：改 allkeys-lfu 或扫描路径走旁路（独立实例）。
