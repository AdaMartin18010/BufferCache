## 1. 双机制的成本结构

| 机制 | 触发 | 成本支付方 | 内存滞留 |
| ---- | ---- | ---------- | -------- |
| 惰性删除 | 命令访问到过期 key 时 | 访问路径的延迟（GET 一次过期检查 O(1)） | key 无人访问则**永久滞留** |
| 定期删除 | serverCron（每 ~100ms）采样过期字典 | 后台循环的 CPU（可控预算） | 滞后有界（见 §2） |

**纯惰性的内存风险**：写后永不读的 key（如一次性 token）只增不减——必须定期删除兜底。**纯定期的 CPU 风险**：过期 key 密集时循环超时。Redis 采用两者混合（官方设计，B 级）。

## 2. 定期删除的采样统计学

定期删除每次从过期字典随机采样 `ACTIVE_EXPIRE_CYCLE_LOOKUPS_PER_LOOP`（默认 20，源码常量）个 key，删除其中过期者；若过期占比 ≥ 25% 则继续循环，否则本轮结束（源码 `activeExpireCycle` 逻辑，B 级）：

- **清理速率上界**：单轮 ≈ 100ms × (20 × 循环数)，循环数由过期密度自适应。
- **滞后时间估算**（推导自采样统计，C 级）：设过期速率 $\lambda_e$（key/s），系统可持续条件是 $\lambda_e \leq R_{clean}$（清理速率）；滞后量 = 积累差 × 平均滞留时长。TTL 集中的场景（大量 key 同刻过期）$\lambda_e$ 瞬时超 R_clean → 滞后峰值。
- **自适应保护**：过期占比 <25% 就停止的阈值设计，是 CPU 与滞后的平衡点（源码注释明确该权衡）。

## 3. 过期风暴的形成条件

过期风暴 = 单位时间过期量持续超过清理速率，表现为：

1. **TTL 高度集中**：同一秒级 TTL（如全部 `SETEX key 3600` 同一时刻写入）→ 同刻过期洪峰。**缓解**：TTL 加随机抖动（[04.04.02 雪崩治理](../../04-架构设计/04.04-缓存问题与治理/04.04.02-缓存雪崩.md) 的数学依据）。
2. **bigkey 占比高**：单 key 删除成本高（同步 DEL 释放大内存），拖慢清理循环。
3. **观察指标**：`expired_keys` 速率、`expired_subkeys`（8.x 子 key 过期）、CPU 的 `sys` 占比突增、内存下降滞后于 TTL 到点。

## 4. 大 key 过期阻塞与 UNLINK

- 惰性删除与定期删除传统上用**同步 DEL**：释放 bigkey（如 100MB 的 list）的内存分配块（jemalloc 归还给 arena）在调用路径上完成 → **阻塞事件循环数十 ms**。
- **UNLINK（4.0+）**：仅把 key 从字典摘除（O(1)），内存释放移交后台线程异步完成（官方 UNLINK 文档，B 级）。
- 定期删除在 4.0+ 已改用 UNLINK 语义（unlink 化），但单 key 摘除 + 桶处理仍有成本；**生产建议**：应用侧删大 key 一律 UNLINK，定期任务避开大 key 集中过期窗口。

## 5. 与持久化的交互

| 交互 | 行为 | 依据 |
| ---- | ---- | ---- |
| RDB 快照 | 已过期的 key 不写入快照；未过期但将过期的写入后，加载时惰性检查 | RDB 持久化文档 |
| AOF | 过期删除以 DEL/UNLINK 形式追加到 AOF（保证从库一致删除） | AOF 重写文档 |
| 混合重写 | 重写时跳过已过期 key；对即将过期者按剩余 TTL 保留 | 源码重写逻辑 |

**推论**：AOF 的过期删除记录使 AOF 体积略大于数据态；重写后收敛。
