# 03.06.07 客户端连接与重试行为矩阵

> 同一个 Redis 集群，用不同客户端、不同默认配置接入，故障行为截然不同——有的静默重试放大风暴，有的快速失败。本文矩阵化主流客户端的默认行为与生产必须显式配置的关键参数，作为接入评审的检查表。

## 1. 概述：客户端是故障行为的放大器

Redis 服务端是单线程、无队列背压的（[03.06.06 背压治理](03.06.06-客户端缓冲与背压治理.md)），**过载保护的很大部分职责落在客户端**：

- 无界重试 × 多实例 = 重试风暴（故障自我放大，[07.09.02](../../07-运维与部署/07.09-弹性伸缩与自愈/07.09.02-自愈机制实践.md) §4 修复闭环的"动作幂等"在客户端侧的对应物）。
- 拓扑刷新时机决定 Cluster 故障转移后多快恢复（[07.05.03 故障转移](../../07-运维与部署/07.05-集群管理/07.05.03-集群故障处理.md) 的客户端侧变量）。
- 连接池耗尽的表现差异（阻塞等待 vs 快速失败）。

## 2. 行为矩阵

| 客户端 | 默认超时 | 默认重试 | 拓扑刷新 | 连接池 | 备注 |
| -------- | -------- | -------- | -------- | ------ | ---- |
| Jedis（Java） | 2s（socket） | 不重试 | Cluster 模式 MOVED 触发刷新 | JedisPool 有界 | 非 Cluster 需自己处理 failover |
| Lettuce（Java） | 60s（默认长） | 不重试（命令级可配） | 永久订阅集群拓扑（自适应） | 共享连接（单连接多路复用） | 生产默认首选；超时必须显式配 |
| redis-py（Python） | 无默认 socket_timeout！ | 不重试 | Cluster 客户端按 MOVED 刷新 | ConnectionPool 有界 | **无默认超时是头号坑** |
| go-redis（Go） | 3s dial / 无读超时 | 不重试（MaxRetries 默认 0） | Cluster 自动刷新 | 池化（PoolSize 默认 10×CPU） | 默认行为保守安全 |
| redis-rs（Rust） | 无默认（依 tokio 配置） | 不重试 | Cluster 支持有限 | 无内建池（用 bb8/fred） | 需显式配 |
| node-redis（Node.js） | 无默认超时 | 自动重连（指数退避） | 自动 | 单连接 | 重连风暴需 disableOfflineQueue 治理 |
| hiredis（C） | 无 | 无 | 无 | 无 | 裸协议库，行为全自定义 |

**矩阵结论**（B 级官方文档默认值 + C 级经验归纳）：**默认配置全部不能直接上生产**——超时、重试上限、拓扑刷新三处必须显式声明。

## 3. 重试设计的四个决策点

| 决策点 | 选项 | 依据 |
| ------ | ---- | ---- |
| 哪些命令可重试 | 只读命令（GET/EXISTS）+ 幂等写（SET key=v，天然幂等）；**不可重试**：INCR/LPOP/PUSH（非幂等） | 命令语义（B 级） |
| 重试次数与退避 | ≤3 次，指数退避（base 50ms × 2^n + jitter），总预算 ≤500ms | 重试窗口应远小于调用方超时（C 级经验） |
| 重试放大防护 | 客户端熔断（连续失败 N 次 → 快速失败 30s）+ 全局限流（单实例重试 QPS 上限） | [02.06.01 熔断](../../02-系统实现/02.06-程序设计实践/02.06.01-容错机制设计.md) |
| 超时预算分配 | 连接超时 < 读超时 < 调用方总超时（如 100ms/300ms/1s） | 超时级联原则（B 级工程原则） |

## 4. 生产配置基线（按语言）

```python
# redis-py 基线
Redis(host=..., socket_connect_timeout=0.1, socket_timeout=0.3,
      retry_on_timeout=False,   # 超时不重试（或仅对 GET 重试）
      health_check_interval=30, # 池化连接活性检查
      max_connections=100)
```

```java
// Lettuce 基线
ClientOptions.builder()
  .socketOptions(SocketOptions.builder().connectTimeout(Duration.ofMillis(100)).build())
  .timeoutOptions(TimeoutOptions.enabled(Duration.ofMillis(300)))
  .autoReconnect(true)   // 断连重连≠命令重试
  .build();
// 命令重试用 RetryExecutor 仅包裹只读命令
```

```go
// go-redis 基线
&redis.Options{
  DialTimeout: 100 * time.Millisecond,
  ReadTimeout: 300 * time.Millisecond,
  MaxRetries:  2,              // 仅对可重试错误（连接类）生效，非幂等命令客户端不自动重试
  PoolSize:    50,
  MinIdleConns: 10,
}
```

## 5. 接入评审检查表

1. 所有 Redis 调用点是否有显式超时（grep socket_timeout/timeoutOptions 配置来源）？
2. 重试策略文档化：次数/退避/哪些命令——评审时要求给出命令清单。
3. 熔断器是否在 Redis 客户端外层（防止 Redis 故障拖垮调用方线程池）？
4. 连接池上限与调用方并发模型的匹配（池等待队列长度 × 线程数 ≤ 可接受阻塞总量）？
5. Cluster 拓扑刷新策略是否显式（默认自适应 vs 定时刷新）？
6. 慢日志与客户端超时告警是否关联（[04.04.07 指标体系](../../04-架构设计/04.04-缓存问题与治理/04.04.07-缓存监控指标体系.md)）？
