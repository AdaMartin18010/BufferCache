## 1. 概述

缓存的共享性与时序性使其成为信息泄露与操纵的天然攻击面。缓存安全问题横跨四个层次：

| 层次 | 攻击目标 | 典型攻击 | 后果 |
| ---- | -------- | -------- | ---- |
| CPU 微架构缓存 | 加密密钥、秘密数据 | 侧信道（时序泄露） | 机密性破坏 |
| 操作系统页缓存 | 跨进程/容器数据 | 预热攻击、页故障通道 | 机密性破坏 |
| Web/CDN 缓存 | 大量用户内容 | 缓存投毒/污染 | 完整性/可用性破坏 |
| 应用缓存（Redis等） | 业务数据与服务 | 未授权访问、键操纵 | 数据泄露/篡改 |

**统一视角**：缓存安全 = 缓存的**共享**（多用户复用同一存储）与**命中/缺失的可观测性**（时序差异）构成的攻击面。防护的本质是切断"共享"（隔离/分区）或消除"可观测性"（随机化/常数时间）。

## 2. CPU缓存侧信道攻击

### 2.1 攻击原语

现代 CPU 缓存的攻击建立在两个硬件事实上：

1. **缓存命中与缺失的时延差**（~1ns vs ~100ns 内存）可被精确测量（`rdtsc`）
2. **缓存状态可被攻击者观测或操纵**（共享行、冲突集）

### 2.2 Flush+Reload

- **前提**：攻击者与受害者共享物理内存页（库文件、共享内存、去重页）
- **步骤**：`clflush` 逐出目标缓存行 → 等待受害者执行 → 重新加载测量时间。命中 ⇒ 受害者访问过该行
- **精度**：缓存行级（64B），单条加载可判定
- **经典案例**：跨 VM 恢复 AES 密钥（Gülmezoğlu et al.）、恢复 EdDSA 密钥

### 2.3 Prime+Probe

- **前提**：无需共享内存，只要求共享缓存组（如 LLC 的同一 set）
- **步骤**：用攻击者数据填满某缓存组（Prime）→ 等待 → 测量重新填充各行的耗时（Probe）。耗时异常的行 ⇒ 受害者访问了同组数据
- **用途**：云环境跨 VM/跨容器攻击（构建 LLC 冲突集）、构建受害者的访问轨迹
- **变体**：Flush+Flush（以 flush 指令自身时延为信号，不触发内存加载，更隐蔽）

### 2.4 投机执行攻击（Spectre/Meltdown）

投机执行产生的瞬态内存访问会修改缓存状态，即使结果被回滚，**缓存痕迹保留**：

```text
Spectre v1（边界检查绕过）：恶意训练分支预测器 → 瞬态越界读 → 通过缓存通道传递
Meltdown：用户态瞬态读取内核内存 → 缓存侧信道恢复
```

**启示**：缓存是投机攻击的"传声筒"——所有投机类攻击（2018 年后数十种变体）几乎都以缓存侧信道收尾。防护因此分为两类：堵住投机（retpoline、lfence、硬件修复）与消除痕迹（瞬态访问不进入缓存，如 InvisiSpec 类研究方案）。

### 2.5 TLB侧信道

TLB（地址转换缓存）同样具备命中/缺失时延差，且**地址转换行为泄露访问的页粒度位置**（与数据内容无关）：

- 通过操纵页表项的 Present bit 触发缺页，或通过 Evict+Time 测量 sTLB 组
- 可绕过部分缓存防护（防御者加固了 L1，却忽略了 TLB）
- 缓解：与缓存防护同源的随机化与刷新，但成本更高（TLB 抖动影响性能）

### 2.6 云环境与机密计算

- **跨 VM LLC 攻击**：同机不同 VM 共享 LLC，Prime+Probe 可窃取邻居 VM 的加密流量密钥（研究已演示于 AES、RSA 的端到端恢复）
- **AMD SEV/SEV-SNP**：2023 年 **CacheWarp**（CVE-2023-20592）利用 INVD 指令语义使加密 VM 的缓存行失效而不写回，导致虚拟机状态回滚，破坏完整性保证；2025 年披露针对 SEV 的缓存侧信道（CVE 系列）——机密计算并非侧信道免疫
- **Intel TDX**：研究揭示 TDX 环境仍存在主机诱导的中断/异常通道、性能计数器通道、缓存通道等攻击面
- **缓解方向**：机密 VM 的缓存分区（SEV 的 VMSA/缓存行为控制）、避免与不可信邻居共享 LLC（调度器亲和）

## 3. Web与CDN缓存攻击

### 3.1 Web缓存投毒（Cache Poisoning）

攻击者构造恶意请求，使缓存存储**攻击者控制的内容**并分发给后续用户：

- **键操纵**：缓存键未包含决定响应的 Header（如 Host、X-Forwarded-Host、User-Agent、Accept-Language），注入 `X-Forwarded-Host: evil.com` 使缓存存储指向恶意域的响应
- **动态内容污染**：反射型 XSS 载荷进入可缓存响应（如错误页面包含未转义的请求 URI），所有命中者执行脚本
- **探测方法**（PortSwigger 方法论）：识别可缓存响应 → 发现未键控的输入 → 观察对响应的影响 → 构造可传播载荷

### 3.2 CPDoS：缓存污染拒绝服务

CPDoS（Cache Poisoned Denial of Service，2019）利用 HTTP 缓存对**错误响应**的缓存规则：

1. 攻击者发送带畸形 Header 的请求（如超长 `X-HTTP-Method-Override`）
2. 源站返回错误（400/500 等）或攻击者触发未处理异常路径
3. 缓存按配置缓存了该错误响应（`Cache-Control: max-age` 在错误响应上生效）
4. 后续正常请求命中缓存，收到错误——**服务被"缓存级"下线**

变种包括阻塞前端请求头解析、缓存规则与源站行为的组合漏洞。**防护**：仅缓存 200 响应、对错误响应忽略缓存指令、Header 大小限制。

### 3.3 DNS缓存投毒

- **Kaminsky 攻击（2008）**：利用 UDP 源端口与事务 ID 的有限熵，向解析器洪水注入伪造应答，毒化任意域名记录
- **缓解**：源端口随机化、事务 ID 熵增、0x20 随机大小写、DNSSEC
- **持续风险**：CVE-2025-40778（BIND 未请求资源记录的缓存投毒）等实现层缺陷说明该攻击面仍在演化

### 3.4 构建系统与CI缓存投毒

2025 年披露的新攻击类：**CI 缓存成为跨工作流/跨分支的持久存储面**。攻击者利用缓存键的可预测性或权限边界缺陷，向共享缓存（npm 缓存、Docker 层、构建产物）注入恶意内容，使后续构建复用被污染的产物——供应链安全的缓存维度。

## 4. 应用层缓存安全

### 4.1 缓存键完整性

应用缓存（Cache-Aside 等模式）的安全前提：**缓存键必须完整编码影响数据内容的所有维度**：

- **反例**：键 = `user:{id}`，但内容受角色/租户影响且未编码进键 → 跨租户数据泄露（缓存键冲突 = 授权绕过）
- **键注入**：用户可控数据进入键（如拼接未过滤的查询参数）→ 键空间污染或命中他人数据
- **防护**：键规范化（排序参数、剔除未授权维度）、内容寻址（哈希 + 版本）、租户/权限维度强制入键

### 4.2 Redis安全风险

- **暴露面**：默认绑定 0.0.0.0、无密码、6379 端口——历史上大量未授权访问事件（数据窃取、勒索写入）
- **加固基线**：绑定内网地址、requirepass/ACL 最小权限、rename-command 禁用 FLUSHALL/CONFIG、TLS、Unix socket、防火墙白名单
- **Lua 沙箱**：脚本在服务器执行，不可信脚本可阻塞/耗尽——限制脚本来源与 EVALSHA 使用
- **模块风险**：第三方模块以 Redis 进程权限运行（C 代码），供应链审计必需

## 5. 缓解与防护

### 5.1 缓存分区与隔离

- **Intel CAT / AMD QoS**：将 LLC 划分为分区，安全敏感负载独占分区，消除 LLC 侧信道的共享前提
- **缓存锁**（`CLDEMOTE`/LLC pinning）：关键数据常驻，避免被驱逐/探测
- **物理隔离**：安全关键进程独占核心与缓存域（云场景对应"裸金属/独占实例"）

### 5.2 随机化与混淆

- **缓存索引/行随机化**：硬件或加密地址变换使攻击者无法构造确定性冲突集（学术方案如 CEASER、ScatterCache）
- **添加噪声**：随机填充缓存访问、随机延迟——降低信噪比，但无法根除

### 5.3 常数时间编程

密码学实现的黄金标准：消除密钥相关的分支与内存访问模式（S-box 查表 → 位运算实现；蒙哥马利阶梯替代条件减法）。注意：常数时间代码仍可能被**微架构优化**（投机执行、缓存压缩、预取）重新引入泄漏——需结合验证工具（dudect、t-test 泄漏检测）。

### 5.4 软件防御与调度

- **上下文切换缓存清理**：高安全环境切换时冲刷 L1（Linux 已有 per-context 开关，成本显著）
- **核心调度（core scheduling）**：互相不信任的任务不共享 SMT 兄弟线程——切断 L1/L2 共享通道
- **页着色（page coloring）**：OS 层将安全域的页映射到不相交的缓存组
- **flush-on-demand**：敏感操作前主动 `clflush`/`wbinvd`

### 5.5 Web缓存防护

1. 仅缓存成功响应（200），错误响应绝不缓存
2. 缓存键包含全部内容决定维度（Host、协议、端口、关键 Header 白名单）
3. 对外部输入严格校验，不反射未转义内容到可缓存响应
4. 分割缓存命名空间（按租户/应用），配合同步失效
5. 定期进行缓存投毒回归测试

## 6. 威胁建模与检查清单

**CPU 侧信道场景**：

- [ ] 多租户/多 VM 共享物理机？→ 评估 LLC 隔离（CAT/裸金属选项）
- [ ] 处理密钥的进程与不可信进程同 SMT 核？→ core scheduling
- [ ] 加密原语是否常数时间且经泄漏检测验证？
- [ ] 机密计算环境是否评估了缓存/TLB 通道（SEV/TDX 已知 CVE）？

**Web 缓存场景**：

- [ ] 错误响应（4xx/5xx）是否被缓存？
- [ ] 缓存键是否包含所有内容决定维度？
- [ ] 是否存在未键控的反射输入进入可缓存响应？
- [ ] DNS 解析器是否开启端口随机化与 DNSSEC 验证？

**应用缓存场景**：

- [ ] 缓存键是否编码租户/权限维度？
- [ ] Redis 是否启用 ACL、绑定内网、禁用危险命令？
- [ ] CI 缓存键是否可预测/跨信任域共享？
