## 1. 概述

### 1.1 定义与背景

**KV Cache（键值缓存）**是大模型推理过程中，为避免自回归生成的重复计算而缓存的历史 token 的注意力键（Key）和值（Value）张量。自 2023 年起，KV Cache 从推理引擎的"内部实现细节"演变为**一等资源**：其管理方式直接决定推理系统的吞吐、延迟和成本，形成了与操作系统 Buffer Cache 高度同构的研究与工程领域。

**发展脉络**：

- **2022（OSDI）**：Orca 提出 continuous batching（连续批处理），奠定迭代级调度基础
- **2023.06（SOSP）**：vLLM 提出 PagedAttention，将 OS 虚拟内存分页思想引入 KV Cache 管理
- **2023.11-2024.01（NeurIPS 2024）**：SGLang 提出 RadixAttention，以前缀基数树实现跨请求 KV 复用
- **2024（OSDI）**：DistServe、Sarathi-Serve 分别确立 P/D 分离与 chunked prefill 两条路线
- **2024-2025**：Mooncake（Kimi 生产系统，FAST 2025）确立"以 KV Cache 为中心"的分离式架构；LMCache、HiCache 等将分层存储工程化
- **2025+**：KV Cache 池化成为大模型推理集群的标准基础设施，与调度器、网络、存储协同设计

### 1.2 与传统Buffer Cache的谱系关系

LLM KV Cache 管理是经典缓存问题在新硬件形态上的实例化，几乎每一项技术都有对应的传统缓存原型：

| 传统缓存概念 | LLM KV Cache 对应物 | 代表系统 |
| ------------ | -------------------- | -------- |
| 虚拟内存分页 | PagedAttention 块管理 | vLLM |
| 页表 / TLB | Block Table / block hash | vLLM、SGLang |
| 前缀缓存（如 Web 缓存共享前缀） | Prefix Caching / RadixAttention | vLLM APC、SGLang |
| 内存层级（Cache-DRAM-SSD） | HBM→DRAM→SSD→Remote 分层 | FlexGen、LMCache、HiCache |
| 缓存淘汰（LRU/LFU） | 前缀块 LRU 驱逐 | SGLang RadixAttention |
| 缓存命中率与栈距离 | 前缀复用率、前缀长度分布 | 全系统 |
| 缓存一致性（多副本） | 分布式 KV 池的一致性语义 | Mooncake、NIXL |

**核心差异**：传统 Buffer Cache 缓存的是"数据块"（内容寻址），KV Cache 缓存的是"计算状态"（token 序列位置寻址 + 模型版本 + 采样参数绑定），因此复用条件更严格、失效语义更复杂（模型权重更新即全量失效）。

## 2. KV Cache基础与内存模型

### 2.1 KV Cache的工作原理

自回归生成中，第 $t$ 个 token 的注意力计算需要与全部历史 token 的 Key/Value 交互。朴素实现每步重新计算全部历史的 K/V，复杂度为 $O(t^2)$；缓存历史 K/V 后，每步只需计算新 token 的 Q/K/V 并与缓存 K/V 做注意力，复杂度降为 $O(t)$（每步增量）。

**代价**：缓存本身占用显存，且随序列长度线性增长。当并发请求数高、上下文长时，KV Cache 而非模型权重成为显存的主要占用者。

### 2.2 KV Cache的容量模型

设模型层数为 $L$，注意力头数为 $h$（每头维度 $d_h$），K/V 各占一份，KV Cache 每 token 的显存占用为：

$$M_{token} = 2 \times L \times h \times d_h \times b_{bytes}$$

其中 $b_{bytes}$ 为单元素字节数（FP16=2，FP8=1，INT4≈0.5）。注意 $h \times d_h = d_{model}$（标准 MHA），因此：

$$M_{token} = 2 \times L \times d_{model} \times b_{bytes} \qquad \text{(MHA)}$$

**示例（MHA，FP16）**：Llama-70B 类模型（$L=80$, $d_{model}=8192$）：

$$M_{token} = 2 \times 80 \times 8192 \times 2 = 2.62\ \text{MB/token}$$

1 个 128K 上下文的请求即需约 336 GB——远超单卡 80GB 显存。这正是 KV Cache 管理成为核心问题的根本原因。

**并发容量估算**：可用 KV 显存 $M_{KV}$ 时，最大并发 token 数：

$$N_{tokens}^{max} = \frac{M_{KV}}{M_{token}}$$

### 2.3 注意力架构对KV Cache的影响（MHA/GQA/MQA/MLA）

| 架构 | 原理 | KV 体量 | 代表 |
| ---- | ---- | ------- | ---- |
| MHA（多头注意力） | 每头独立 K/V | 基准 $2L \cdot d_{model}$ | 早期 Transformer |
| GQA（分组查询注意力） | 多查询头共享一组 K/V | 约 $1/G$（$G$ 为组大小） | Llama-2/3、Qwen |
| MQA（多查询注意力） | 全部查询头共享一份 K/V | $h$ 倍缩减 | PaLM、ChatGLM |
| MLA（多头潜在注意力） | K/V 低秩联合压缩为潜在向量 | 约 $1/4 \sim 1/7$ | DeepSeek-V2/V3 |

**MLA 细节（DeepSeek）**：将 K/V 投影到低秩潜在空间，缓存压缩后的潜在向量（latent vector）而非完整 K/V，注意力计算时再上投影。缓存量从 $2 \times L \times d_{model}$ 降至约 $L \times d_c$（$d_c$ 为潜在维度，通常 $d_c \ll d_{model}$）。这是对"缓存什么"的架构级回答——与"如何管理缓存"的系统级方案（分页/分层）正交且可叠加。

## 3. 页式管理：PagedAttention与vLLM

### 3.1 设计思想：操作系统虚拟内存的借鉴

vLLM（Kwon et al., SOSP 2023）的核心观察：朴素 KV Cache 分配为每个请求预留连续显存块，存在两类浪费：

- **内部碎片**：为最大长度预留，实际用不满
- **外部碎片**：连续分配要求导致空闲显存被切割，无法利用

PagedAttention 将 OS 虚拟内存机制完整映射到 KV Cache：

| OS 虚拟内存 | PagedAttention |
| ----------- | -------------- |
| 物理内存页（4KB） | KV Block（16 token，可配置） |
| 虚拟地址空间 | 请求的逻辑 token 序列 |
| 页表（Page Table） | Block Table（块表） |
| 按需分页分配（demand paging） | 按需分配 KV Block |
| 页置换（swap） | Block 驱逐/换出 |
| 写时复制（COW） | 分支序列共享物理块（如 beam search、共享前缀） |

**效果**：显存利用率从静态分配的 <30% 提升至 ≥96%，吞吐提升 2-4 倍。

### 3.2 核心数据结构

```python
# PagedAttention 核心数据结构示意
class PagedKVCache:
    def __init__(self, num_blocks: int, block_size: int, num_layers: int,
                 num_heads: int, head_dim: int):
        # 物理块池：所有请求共享的全局显存池
        # shape: [num_blocks, block_size, num_heads, head_dim]
        self.key_blocks = allocate(num_blocks, block_size, num_heads, head_dim)
        self.value_blocks = allocate(num_blocks, block_size, num_heads, head_dim)
        self.free_block_queue = list(range(num_blocks))  # 空闲块队列

    def allocate(self, num_tokens: int) -> BlockTable:
        """按需分配物理块，逻辑连续、物理离散"""
        num_needed = ceil(num_tokens / self.block_size)
        blocks = [self.free_block_queue.popleft() for _ in range(num_needed)]
        return BlockTable(blocks)  # 逻辑token -> 物理块映射

    def free(self, table: BlockTable):
        """释放块回空闲池"""
        for b in table.blocks:
            self.free_block_queue.append(b)
```

**Block Table** 记录每个请求的逻辑 token 块到物理块的映射，注意力内核通过查表完成非连续访存。

### 3.3 内存分配与回收流程

1. **Prefill 阶段**：按 prompt 长度分配足量 block（最后一个块按需部分填充）
2. **Decode 阶段**：每生成一个 token，检查当前块是否写满；写满则分配新块
3. **驱逐压力**：空闲块耗尽时，触发抢占（preemption）——vLLM 支持：
   - **Swapping**：将被抢占请求的 KV Block 换出到 CPU 内存
   - **Recomputation**：丢弃被抢占请求的 KV，后续重新 prefill（以计算换显存）
4. **完成回收**：请求结束后释放全部 block 回全局池

### 3.4 与前缀缓存的结合

PagedAttention 的块结构天然支持前缀共享：多个请求具有相同 prompt 前缀时（如相同系统提示词），前缀块可被引用计数共享，无需复制。vLLM 的 Automatic Prefix Caching（APC）将块哈希（本块 token + 前缀链哈希）作为缓存键，命中时直接复用物理块，跳过对应前缀的 prefill 计算。

### 3.5 vLLM V1引擎架构

2025 年 vLLM 完成 V1 引擎重写（早期版本称 V0）：

- **调度器与执行分离**：Scheduler 纯 CPU 侧决策，执行层异步调度 GPU kernel
- **降低 CPU 开销**：V0 中 Python 调度开销成为瓶颈，V1 重构关键路径
- **统一多模态与新架构支持**：模块化 executor 支持 Attention 后端插件化（FlashAttention、FlashInfer、FlexAttention 等）
- **KV Connector 抽象**：标准化的跨实例 KV 传输接口，支撑 P/D 分离（见第 6 节）

## 4. 前缀复用：RadixAttention与SGLang

### 4.1 RadixAttention的基数树设计

SGLang（Zheng et al., NeurIPS 2024）的 RadixAttention 将前缀缓存组织为**基数树（Radix Tree）**：

- 树的每条边标记一段 token 序列，节点保存该路径前缀的 KV Cache 块引用
- 新请求到来时沿树匹配最长公共前缀，命中的前缀直接复用，仅对剩余后缀做 prefill
- 生成完成后，新序列插入树中，供后续请求复用
- 适合结构化 prompt 场景：多轮对话（历史即前缀）、few-shot 示例、共享系统提示、Agent 工具调用循环

**与 vLLM APC 的差异**：APC 以"块哈希表"为索引，匹配粒度为固定块；RadixAttention 以树为索引，支持更灵活的前缀匹配与按需分裂/合并节点，并配合调度器做缓存感知的请求放置。

### 4.2 LRU淘汰与缓存感知调度

RadixAttention 为树节点维护 **LRU 状态**，显存不足时按 LRU 驱逐叶子节点（释放其 KV 块）。调度（cache-aware scheduling）将请求路由到持有其前缀的节点/设备，提高命中率——这与传统缓存中的"缓存亲和性负载均衡"（如一致性哈希 + 本地缓存）思想完全一致。

### 4.3 vLLM Automatic Prefix Caching

vLLM APC 实现要点：

- **块哈希链**：第 $i$ 块的键 = hash（本块 token 序列, 第 $i-1$ 块哈希），保证前缀链完整性
- **LRU 驱逐**：空闲块不足时驱逐最久未使用的缓存块
- **完全共享**：命中块的引用计数 +1，多请求共享物理块，全部释放后块回空闲池
- **零开销查找**：哈希表 O(1) 查找，调度路径无额外开销

### 4.4 前缀复用的命中率分析

前缀缓存收益可用复用率 $r$（命中前缀 token 数 / 总 prompt token 数）刻画。设 prefill 吞吐 $T_{prefill}$（token/s），命中 $L_{hit}$ 个前缀 token 可节省时间：

$$\Delta t_{TTFT} = \frac{L_{hit}}{T_{prefill}}$$

命中率分布高度依赖负载：多轮对话/Agent 场景前缀复用率可达 60-90%；独立短请求场景趋近于 0。**容量规划启示**：prefix cache 池大小应覆盖工作集的前缀热度分布（与传统缓存的"工作集模型"相同，见 [LRU文档](../01-理论基础/../../01-理论基础/01.01-基础替换算法/01.01.01-LRU算法原理与实现.md) 第 3.1.2 节）。

## 5. 分层卸载：多级KV Cache存储

### 5.1 为什么需要分层

HBM 容量有限而 KV Cache 需求随上下文长度与并发数增长。参考传统存储层次的成本-延迟结构，KV Cache 自然形成分层：

| 层级 | 容量 | 带宽 | 典型用途 |
| ---- | ---- | ---- | -------- |
| GPU HBM | 80-192 GB/卡 | 数 TB/s | 当前 decode 活跃工作集 |
| CPU DRAM | TB 级 | 数百 GB/s | 换出/待复用前缀 |
| 本地 NVMe SSD | 数 TB | 数 GB/s | 长前缀、会话恢复 |
| 远端存储/缓存池 | PB 级 | 数百 MB/s | 跨实例共享、成本层 |

**复用价值驱动分层**：被驱逐的前缀块若未来被复用，重新 prefill 的成本远高于从低层取回的 I/O 成本——只要 $T_{reload} < T_{reprefill}$，分层就是净收益。

### 5.2 FlexGen：单卡GPU-CPU-SSD分层

FlexGen（2023）面向单卡高吞吐离线推理，将权重、激活、KV Cache 三者统一做分层放置与块调度（block scheduling）：不活跃的层换出到 CPU/SSD，GPU 只保留当前计算所需部分。以延迟换吞吐，将百亿级模型推理压入消费级硬件。其启发式放置策略（z-size 划分、重叠调度）是存储层次优化的经典实现。

### 5.3 LMCache：生产级分层卸载

LMCache（2025）是面向生产的 KV Cache 分层缓存层：

- **跨引擎**：同时对接 vLLM 与 SGLang，缓存格式引擎无关
- **跨层级**：Host RAM → 本地 NVMe → 远端存储（如 Redis/对象存储）多级
- **两类复用**：prefix-reuse offloading（前缀复用卸载）与 P/D 分离传输加速
- **流水化**：批量数据移动、计算与 I/O 流水线重叠、GPUDirect Storage 直传（跳过 CPU 内存 bounce buffer）

### 5.4 CacheGen：KV Cache压缩传输

CacheGen（Liu et al., 2024）针对跨设备 KV 传输的带宽瓶颈，将 KV 张量压缩编码（利用相邻 token KV 的数值相关性），传输后解码还原，以编码/解码开销换取数倍带宽节省，适合 P/D 分离与远端缓存场景。

### 5.5 SGLang HiCache多级缓存

SGLang HiCache（2025.11）将多级内存层次（HBM→DRAM→SSD）纳入引擎原生管理：RadixAttention 树的节点可驻留不同层级，调度器按访问热度自动升降级（promotion/demotion）——与 OS 的 memory tiering（如 DAMON/demotion，见 [02.04 现代内核缓存机制]）机制同构。

## 6. 分离式架构与分布式KV池

### 6.1 Prefill/Decode资源画像差异

| 阶段 | 计算特征 | 显存特征 | 瓶颈 |
| ---- | -------- | -------- | ---- |
| Prefill | 计算密集（GEMM 大矩阵） | 突发占用（整段 prompt 一次性入显存） | 算力、TTFT |
| Decode | 访存密集（每步批量小 GEMV） | 持续占用（KV Cache 驻留整个生成过程） | 显存带宽、TPOT |

两者共置（colocate）时：prefill 的算力峰值期 decode 被饿延迟，decode 的显存高压期 prefill 无处分配——相互干扰。分离（disaggregation）后各自独立扩缩容与并行策略。

### 6.2 DistServe：P/D分离

DistServe（Zhong et al., OSDI 2024）首次系统化 P/D 分离：

- Prefill 池与 Decode 池物理分离，各自配置并行策略（prefill 用激进张量并行压低 TTFT，decode 用大 batch 提升吞吐）
- 请求在 prefill 完成后，将其 KV Cache 经高带宽网络迁移到 decode 池
- **Goodput** 优化目标：满足 SLO（TTFT/TPOT 上限）前提下的最大吞吐

### 6.3 Mooncake：以KV Cache为中心的分离架构

Mooncake（Qin et al., Kimi 生产系统，FAST 2025）代表当前工业界最高水平：

- **KVCache-centric**：把 KV Cache 从"设备私有状态"转为"分布式可复用对象"，架构围绕全局 KV Cache 池设计
- **分离 + 分层**：Prefill/Decode 池分离；KV Cache 池横跨 HBM、DRAM、SSD
- **以 KV 为中心的调度**：调度器权衡复用收益、传输成本、排队时延、计算成本与 SLO 的总成本做全局决策
- **逐层传输（layer-wise pipelining）**：KV 按 Transformer 层流水线式传输，首层到达即可开始计算，隐藏传输延迟
- **CPP（Chunked Pipeline Prefill）**：超长 prefill 分块流水化，消除首 token 等待

Mooncake 改变了优化单位：不再是某个 kernel、某张卡或某个 batch，而是"请求携带的计算与状态在整个集群中的生命周期"。

### 6.4 KV传输：NIXL与逐层流水线

P/D 分离的关键路径是 KV Cache 传输。NVIDIA NIXL（Inference Xfer Library）提供生产级点对点传输：GPUDirect RDMA、CPU/SSD 后端统一抽象、与 vLLM KV Connector 集成。配合逐层传输（layer-wise transfer）流水线，传输延迟被计算重叠隐藏。

### 6.5 集群编排：llm-d与Kubernetes

llm-d 将推理服务纳入 Kubernetes 生态：P/D 池作为独立部署单元弹性伸缩，KV 感知的路由（cache-aware routing）将请求导向持有其前缀的 decode 实例——与 CDN 的全局负载均衡 + 边缘缓存亲和设计同构。

## 7. 容量优化：压缩、稀疏与架构创新

### 7.1 DeepSeek MLA：低秩联合压缩

MLA（Multi-head Latent Attention，DeepSeek-V2/V3）将 K 和 V 联合压缩到低秩潜在向量 $c_t^{KV}$：

$$k_t = W_{UK} c_t^{KV}, \qquad v_t = W_{UV} c_t^{KV}$$

缓存 $c_t^{KV}$（维度 $d_c$）替代缓存全部 K/V 头，缓存量降至约 $1/4 \sim 1/7$。配合 FP8 量化，DeepSeek-V3 每 token KV 缓存约 70KB（对比同规模 MHA 模型的 MB 级），使 128K 上下文 + 高并发在有限显存内可行。**启示**：缓存压缩可以在模型架构层一次完成，优于系统层的持续搬运。

### 7.2 KV Cache量化

将 KV 张量从 FP16 降至 FP8/INT8/INT4：

- **按张量/按 token 分组量化**：K 用逐通道（per-channel）、V 用逐 token（per-token）量化以控制误差
- **收益**：显存减半（FP8）至 1/4（INT4），访存带宽同比降低，decode 吞吐提升
- **代价**：注意力精度损失，需校准（group size、舍入模式）；极低比特需 SmoothQuant/KIVI 类技巧

### 7.3 稀疏化与驱逐（StreamingLLM/H2O/SnapKV）

- **StreamingLLM**：利用注意力接收（attention sink）现象，仅保留初始 sink token + 滑动窗口的 KV，无限流式处理
- **H2O（Heavy Hitter Oracle）**：将 KV 驱逐建模为动态子集选择问题，保留累积注意力分数最高的 token
- **SnapKV**：推理前根据观察窗口的注意力模式一次性选择重要 KV 位置，压缩比 3-8 倍，几乎无损

这些方案本质上是**注意力感知的缓存淘汰策略**——从"最近最少使用"升级为"未来最可能被注意"。

## 8. 性能模型与分析

### 8.1 关键指标：TTFT/TPOT/Goodput

| 指标 | 定义 | 决定因素 |
| ---- | ---- | -------- |
| TTFT（首 token 延迟） | 请求到达至首个 token 输出 | prefill 排队 + 计算时间 |
| TPOT（每 token 延迟） | 相邻输出 token 的平均间隔 | decode 批大小、显存带宽 |
| Throughput | 每秒输出 token 总数 | 并发度、批效率 |
| Goodput | 满足 SLO 的吞吐 | 上述全部 + 调度质量 |

### 8.2 Decode的内存带宽模型

Decode 每步为访存密集：权重读取 $W$ 字节，KV 读取随上下文增长。近似单请求 decode 步延迟：

$$t_{step} \approx \frac{W + N_{context} \times M_{token}}{B_{HBM}}$$

其中 $B_{HBM}$ 为显存带宽。大 batch 下权重读取被摊销，瓶颈转向 KV 访存——**KV Cache 大小直接决定 decode 吞吐上限**，这是容量优化（第 7 节）的收益来源。

### 8.3 前缀复用的收益模型

命中前缀长度 $L_{hit}$ 时：

$$\text{TTFT 节省} = \frac{L_{hit}}{T_{prefill}}, \qquad \text{计算节省} = L_{hit} \times 2 \times P \times FLOPs_{per\_token}$$

（$P$ 为模型参数量，prefill 复用省下了对应 FLOPs。）复用率 $r$ 的分布决定缓存池 sizing：按前缀长度分布的第 $p$ 百分位配置容量，使驱逐损失最小化。

### 8.4 分层访问的延迟账

从层级 $i$ 加载 KV 的延迟 $t_i$（含 I/O 与传输）必须小于重新 prefill 的成本：

$$t_{reload} = \frac{Size_{KV}}{BW_i} + t_{transfer} < t_{reprefill} = \frac{Size_{KV}}{KV_{compute\ rate}}$$

DRAM 层通常 10-100 倍满足该条件；SSD 层对长前缀成立；远端层仅在极高复用价值时成立（如跨会话恢复）。这是分层的准入判据（admission policy），与 TinyLFU 的准入思想一致。

### 8.5 动手实验：分页分配与前缀复用模拟

以下纯 Python 脚本（仅标准库）模拟 PagedAttention 的两个核心机制——**物理块池分配**与**前缀缓存复用**，并对比"开/关前缀缓存"的命中率。可直接运行：

```python
# kv_cache_sim.py —— PagedAttention 分页与前缀复用机制模拟（标准库，可直接运行）
from collections import OrderedDict

class BlockPool:
    """模拟 GPU 显存中的 KV 物理块池（每块容纳 block_size 个 token）"""
    def __init__(self, num_blocks: int, block_size: int = 16):
        self.block_size = block_size
        self.free = list(range(num_blocks))          # 空闲物理块
        self.refcount = {}                            # 物理块 -> 引用计数（共享前缀）

    def alloc(self) -> int:
        return self.free.pop()

    def release(self, bid: int):
        self.refcount[bid] = self.refcount.get(bid, 0) - 1
        if self.refcount[bid] <= 0:
            self.free.append(bid)

    def retain(self, bid: int):
        self.refcount[bid] = self.refcount.get(bid, 0) + 1

class PagedKVCache:
    """请求逻辑序列 -> 物理块的映射 + 前缀缓存（块哈希链）"""
    def __init__(self, num_blocks: int, block_size: int = 16, prefix_cache: bool = True):
        self.pool = BlockPool(num_blocks, block_size)
        self.block_size = block_size
        self.prefix_cache = prefix_cache
        self.block_hash = {}      # 哈希 -> 物理块（前缀缓存索引）
        self.usage = OrderedDict()  # LRU 驱逐顺序

    def _hash_block(self, tokens: tuple, prev_hash: int) -> int:
        return hash((tokens, prev_hash))

    def request(self, tokens: list) -> tuple:
        """处理一次请求，返回 (命中token数, 需prefill_token数)"""
        n = len(tokens)
        blocks_needed = (n + self.block_size - 1) // self.block_size
        hit_tokens = 0
        my_blocks = []
        prev_hash = 0
        for i in range(blocks_needed):
            chunk = tuple(tokens[i*self.block_size:(i+1)*self.block_size])
            h = self._hash_block(chunk, prev_hash)
            if self.prefix_cache and h in self.block_hash:
                bid = self.block_hash[h]
                self.pool.retain(bid)
                self.usage.move_to_end(bid)
                hit_tokens += len(chunk)
            else:
                if not self.pool.free:
                    self._evict_lru()
                bid = self.pool.alloc()
                self.pool.retain(bid)
                if self.prefix_cache:
                    self.block_hash[h] = bid
                    self.usage[bid] = h
                hit_tokens += 0  # 本块需 prefill
            my_blocks.append(bid)
            prev_hash = h
        # 释放本请求的独占块（共享块由引用计数保护；简化：前缀缓存模式不释放被缓存块）
        if not self.prefix_cache:
            for bid in my_blocks:
                self.pool.release(bid)
        return hit_tokens, n - hit_tokens

    def _evict_lru(self):
        bid, h = self.usage.popitem(last=False)
        del self.block_hash[h]
        self.pool.release(bid)

def run_workload(num_blocks=64, block_size=16, prefix_cache=True):
    cache = PagedKVCache(num_blocks, block_size, prefix_cache)
    system_prompt = list(range(200))            # 共享系统前缀（200 token）
    total_hit, total_tokens = 0, 0
    for turn in range(50):                       # 50 轮多轮对话
        user_query = [1000 + turn * 10 + i for i in range(20)]
        history = system_prompt + user_query
        hit, miss = cache.request(history)
        total_hit += hit
        total_tokens += hit + miss
    return total_hit / total_tokens

if __name__ == "__main__":
    r_off = run_workload(prefix_cache=False)
    r_on = run_workload(prefix_cache=True)
    print(f"前缀缓存关闭: 复用率 {r_off:.1%}")
    print(f"前缀缓存开启: 复用率 {r_on:.1%}")
    print(f"TTFT 节省（近似）: {(r_on - r_off):.1%} 的 prefill 计算")
```

运行结果（实际执行输出）：

```text
前缀缓存关闭: 复用率 0.0%
前缀缓存开启: 复用率 85.5%
TTFT 节省（近似）: 85.5% 的 prefill 计算
```

**观察要点**：

1. 块哈希链（`_hash_block` 含前一链值）保证前缀完整性——篡改前缀中间任一 token 即断链失效
2. 共享前缀块通过引用计数 + LRU 驱逐管理，与 [ARC 幽灵列表](../01-理论基础/../../01-理论基础/01.02-高级替换算法/01.02.04-ARC自适应替换缓存.md) 的"历史反馈"思想同源
3. 多轮对话场景中复用率趋近 1（历史即前缀），验证了第 4.4 节的命中率分析

## 9. 工程实践指南

### 9.1 容量规划

1. 计算单 token KV 体量（按第 2.2 节公式，注意 GQA/MLA 折减）
2. 确定目标并发数与平均上下文长度，估算峰值 KV 需求
3. 预留 20-30% 给 prefix cache 池与突发增长
4. 显存不足时按优先级启用：GQA/MLA（架构）→ KV 量化 → 分层卸载 → 分离扩容

### 9.2 关键配置参数

| 参数（vLLM 示例） | 含义 | 调优方向 |
| ------------------ | ---- | -------- |
| `gpu_memory_utilization` | KV 池显存占比 | 0.85-0.95，视并发峰值 |
| `block_size` | 分页块大小 | 16（默认）；小值省显存、大值减查表开销 |
| `enable_prefix_caching` | 前缀缓存开关 | 共享前缀场景必开 |
| `max_num_batched_tokens` | 单迭代最大 token 数 | 大值提吞吐、小值降 TTFT |
| `max_num_seqs` | 最大并发序列数 | 按 TPOT 目标权衡 |
| `kv_transfer_config` | P/D 分离传输配置 | 配合 NIXL/Connector |

### 9.3 观测指标

- **GPU KV cache usage / blocks**：显存水位与碎片
- **Prefix cache hit rate**：复用率，低则检查负载结构与容量
- **TTFT / TPOT 分位数**：SLO 达成与尾延迟
- **Preemption / swap 次数**：容量不足信号
- **P/D 传输吞吐与延迟**：分离架构健康度

## 10. 经典缓存理论在KV Cache中的映射

本项目理论基础的直接应用：

| 经典理论 | KV Cache 应用 |
| -------- | ------------- |
| 工作集模型（Denning） | prefix cache 池 sizing：覆盖前缀工作集 |
| LRU 竞争比（Sleator-Tarjan） | RadixAttention LRU 驱逐的最坏情况界 |
| Che 近似 | prefix 命中率的解析预测（以 token 流行度代替对象流行度） |
| 栈距离分布 | 前缀长度分布的复用距离分析 |
| TinyLFU 准入 | 分层卸载的准入判据（$t_{reload} < t_{reprefill}$） |
| 内存分层理论 | HBM→DRAM→SSD 的 promotion/demotion 策略 |
| Little 定律 | 并发数 = 到达率 × 平均请求驻留时间（TTFT+生成时长） |

**开放问题**：注意力感知的淘汰（H2O/SnapKV）突破了"访问驱动"假设，其竞争分析与在线学习理论刻画仍是开放课题；分布式 KV 池的一致性语义（跨节点失效、模型版本绑定）也缺少形式化模型。
