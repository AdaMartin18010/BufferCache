## 1. 概述与范围

云原生缓存的三个承载层次：

| 层次 | 形态 | 运维责任 | 适用 |
| ---- | ---- | -------- | ---- |
| L1 托管服务 | ElastiCache / Memorystore / Azure Managed Redis / Upstash | 云厂商全托管 | 默认选择（2026 年多数组织） |
| L2 K8s 自建 | Operator / Helm / 裸 StatefulSet | 平台团队 | 合规、成本、定制需求 |
| L3 应用内缓存 | Caffeine/ristretto 进程内 + 分布式缓存客户端 | 应用团队 | 多级缓存的第一级 |

Docker 缓存则覆盖两条线：**运行态**（容器镜像内的本地缓存、数据卷缓存）与**构建态**（镜像层缓存、BuildKit cache mounts、CI 缓存）。后者是"缓存即构建加速"的独立工程域。

**趋势一句话**：许可变迁（Redis 7.4 RSAL）重塑了云厂商默认引擎（AWS/GCP 新集群默认 Valkey）；serverless 缓存成为默认入口形态；K8s 侧 Operator 生态收敛至少数几个成熟方案；构建缓存随 CI/CD 成熟成为标准能力。

## 2. 云缓存服务格局（2026）

### 2.1 许可变迁驱动的引擎默认切换

2024-03 Redis 改为 RSALv2/SSPLv1 后，云厂商的引擎策略直接重构（来源：[redisvsmemcached.com 许可时间线](https://redisvsmemcached.com/redis-license-timeline/)，2026 交叉核验）：

| 云厂商 | 服务 | 2024 末后的默认引擎 | 托管 Valkey | 说明 |
| ------ | ---- | ------------------ | ----------- | ---- |
| AWS | ElastiCache（+MemoryDB） | **Valkey（新集群默认）** | ✅ 2024-10 GA | Redis OSS 仍可选 |
| Google Cloud | Memorystore for Valkey | **Valkey（新实例默认）** | ✅ | 另有 Memorystore for Redis Cluster |
| Microsoft Azure | Azure Cache for Redis / Azure Managed Redis | 无托管 Valkey | ❌ | 与 Redis 官方合作推 Azure Managed Redis |

**要点**：新建集群默认 Valkey、存量 Redis OSS 集群不强制迁移——这是 2026 年云缓存选型的第一事实。AGPLv3（Redis 8.0 起可选）对多数企业内部使用无实质负担，但进入法律审查清单；追求纯开源供应链的组织偏好 Valkey/Redict（[03.05 README](../../03-Redis组件/03.05-Redis生态与版本演进/README.md) §3）。

### 2.2 服务模式：Serverless vs 节点式

| 模式 | 代表 | 计费 | 适用 |
| ---- | ---- | ---- | ---- |
| Serverless | ElastiCache Serverless、Memorystore cluster、Upstash | 按用量（容量+请求） | 流量波动大、连接数受限（Lambda/边缘）、快速起步 |
| 节点式 | ElastiCache 节点组、Memorystore 标准层 | 按节点规格 | 稳定高负载、容量规划明确 |
| Per-request | Upstash | 按请求数 | 低频突发、全球 REST 端点 |

Upstash 模式的差异化：HTTP/REST 端点免除连接池管理，适配 Vercel/Cloudflare Workers 等无连接池环境；per-request 计费在低均流量下成本可预测（[Upstash 2026 定价对比](https://upstash.com/blog/redis-pricing-comparison-every-major-provider-in-2026-with-numbers)）。

### 2.3 新玩家：内存数据平台化

- **Dragonfly Cloud**：C++ 多线程实现，宣称单 64 核实例 3.82M ops/s、p99 <0.65ms（第三方基准 [Wise Hustlers 2026-10](https://wise-hustlers.com/blog/dragonfly-vs-valkey-cache-performance-benchmark)，C 级厂商数据需注意基准条件）。
- **Momento Cache**：serverless 缓存 API 化（HTTP/gRPC），面向"缓存即 API"模式。
- **Redis Cloud**：官方托管，功能最全（含模块/向量）。

## 3. Kubernetes 缓存部署模式

### 3.1 模式谱系（按运维负担递减）

```text
裸 StatefulSet（自建 failover/升级）
  → Helm Chart（声明式安装，升级与拓扑仍人工）
  → Operator（CRD 化运维：故障转移/扩缩容/备份自动化）
  → 商业 Operator（Redis Enterprise for Kubernetes：Active-Active、跨集群）
```

### 3.2 Operator 格局（2026-11 核验）

| Operator | 维护方 | 协议 | 状态（2026-11） | 特点 |
| -------- | ------ | ---- | -------------- | ---- |
| **KubeBlocks Redis** | ApeCloud | AGPLv3 | 活跃，1.0.2+ | Sentinel/Cluster 双架构可切换；OpsRequest 统一 CRD（扩缩容/参数/备份）；故障转移 Cluster 4-6s、Sentinel ~30s（[2026-04 实测](https://mdnice.com/writing/b075bead240a4aa4925fddf096c3262a)） |
| **OT-CONTAINER-KIT redis-operator** | Opstree | Apache 2.0 | 活跃，v0.27.0（2026-10-09） | 轻量，standalone/replication/cluster；备份能力相对弱 |
| **Spotahome redis-operator** | Spotahome | Apache 2.0 | **已归档（archived）** | 仅 Sentinel，无 Cluster；新项目勿选（[JusDB 2026-11](https://www.jusdb.com/blog/valkey-redis-operators-kubernetes-compared)） |
| **Redis Enterprise K8s** | Redis 官方 | 商业 | 活跃 | Active-Active 跨集群数据库 |
| **Valkey Helm chart** | valkey-io | BSD | 活跃 | standalone/主从，无 operator |

**要点**：Spotahome 归档后，社区路线收敛到 KubeBlocks（功能最全）与 OT-CONTAINER-KIT（轻量 Apache 2.0）；Bitnami chart 生态收缩（redis-cluster chart 冻结于 13.0.4，镜像 latest 以外不再免费，[acemq 2026-10](https://acemq.com/blogs/redis-on-kubernetes/)），**Valkey 官方 chart 成为 BSD 路线的默认**。

### 3.3 K8s 特有考量

1. **故障转移与 Pod 漂移**：Redis Cluster 的 announce IP 必须与 K8s Service/Pod IP 策略匹配（headless Service + `cluster-announce-ip` 为 Pod IP 或 hostname）；Operator 通常自动处理。
2. **拓扑约束**：Redis 单线程模型下，QPS 密度依赖核频；用 `topologySpreadConstraints` 打散副本，避免同节点。
3. **内存 QoS**：`requests==limits`（Guaranteed QoS）防止驱逐；`maxmemory` 与容器 memory limit 留 20-25% 余量（复制 backlog、AOF、碎片）。
4. **Sidecar 缓存模式**：对无缓存客户端改造的服务，以 Redis proxy sidecar 旁路拦截读请求回源（[oneuptime 2026-03](https://oneuptime.com/blog/post/2026-03-31-redis-sidecar-cache-pattern/view)）；代价是每 Pod 一份资源开销，适合"改造增量小 > 资源效率"的场景。
5. **本地演练环境**：本项目 `Testing/fixtures/redis-lab/` 提供 Compose 版 Cluster/Sentinel 演练环境（见 §4）。

## 4. Docker 与构建缓存

### 4.1 运行态：容器内缓存

- **数据卷缓存**：`volumes` 挂载本地缓存目录（如 Redis AOF 目录、构建 cache dir），容器重建不丢。
- **tmpfs**：`/dev/shm` 挂载用于低延迟场景（对应 `--tmpfs`）。
- **镜像内预热**：构建期把热点数据写入镜像层（只读基础层 + 运行期覆盖），适合只读字典类缓存。

### 4.2 构建态：镜像层与 BuildKit 缓存（成熟度 2026 已标准）

| 机制 | 原理 | 失效控制 | 适用 |
| ---- | ---- | -------- | ---- |
| 层缓存 | Dockerfile 指令有序哈希，未变指令复用层 | 指令顺序敏感 | 依赖安装（先 COPY 依赖清单） |
| BuildKit cache mount | `RUN --mount=type=cache,target=/root/.cache` 持久化构建期缓存目录 | 缓存键（id）+ 不进入镜像层 | 编译缓存（ccache、Maven/Gradle、pip） |
| 外部缓存导出 | `cache-to`/`cache-from`（registry/GHA 后端） | 作用域 registry | CI 流水线跨构建复用 |
| Compose 缓存 | `docker compose build` 复用 BuildKit 同一后端 | 同上 | 本地与 CI 一致性 |

CI 侧：GitHub Actions 的 `actions/cache` 与 BuildKit 的 GHA 缓存后端二选一；关键技巧是**锁文件先行**（COPY package-lock → install → COPY 源码）以最大化层缓存命中。

## 5. 性能与成本分析

### 5.1 性能基线参考（2026 第三方数据，C 级）

| 实现 | 单节点吞吐 | 备注 |
| ---- | ---------- | ---- |
| Redis 8.x | ~100K-1M ops/s（视核频/流水线） | 事件循环单线程 + I/O 线程 |
| Valkey 9.x | 宣称 2.1M RPS（重构 I/O 线程） | [valkey.io](https://valkey.io/) 官方数据 |
| Dragonfly | 宣称 3.82M ops/s @64 核 | 第三方基准条件差异大 |
| Redis Cluster | 线性扩展（3.82M/节点 × N） | 跨槽多键限制 |

> 厂商基准普遍偏乐观（流水线深度、值大小、核数差异大）；选型应以**自身 trace 压测**为准（本项目 [01.05.04](../../01-理论基础/01.05-算法对比与决策/01.05.04-算法性能基准测试.md) 框架）。

### 5.2 成本结构（serverless 时代）

- **Serverless**：小流量（<10GB、波动大）通常更省；高稳态负载下节点式单位成本更低（[Upstash 2026 对比](https://upstash.com/blog/redis-pricing-comparison-every-major-provider-in-2026-with-numbers)）。
- **引擎成本**：Valkey 引擎通常同规格比 Redis OSS 低 20%（AWS/GCP 定价策略）；长期看 Valkey 成为"默认便宜选项"。
- **隐性成本**：跨 AZ 流量费（副本同步）、serverless 请求数费（高频小请求场景）。

## 6. 选型决策

```text
是否允许数据出私有环境？
├─ 否 → K8s 自建：Operator（KubeBlocks/OT-CONTAINER-KIT）或 Valkey Helm
└─ 是 → 流量形态？
    ├─ 波动大/连接受限（Serverless 应用、边缘）→ 云 Serverless（ElastiCache Serverless / Upstash）
    ├─ 稳定高负载 → 节点式 + Valkey 引擎（成本优先）
    └─ 需要模块/向量/Active-Active → Redis Cloud / Azure Managed Redis / Redis Enterprise
许可合规红线：AGPLv3 不可接受 → Valkey（BSD）；可接受 → Redis OSS 8.x
```

## 7. 典型场景

1. **Serverless Web 应用（Vercel + Lambda）**：Upstash REST 端点缓存会话，免除连接池与常驻连接。
2. **电商大促（弹性优先）**：ElastiCache Serverless 基线 + 节点式峰值兜底；预热用 Heat Map 思路（[02.03.06 云数据库预热类比](../../02-系统实现/02.03-数据库缓存/02.03.06-云数据库缓存架构.md)）。
3. **金融合规自建**：K8s + OT-CONTAINER-KIT（Apache 2.0）+ Valkey；审计要求驱动 Operator 化。
4. **本地开发与 CI 演练**：Docker Compose 环境（本项目 `Testing/fixtures/redis-lab/`）+ BuildKit cache mount 加速镜像构建。
