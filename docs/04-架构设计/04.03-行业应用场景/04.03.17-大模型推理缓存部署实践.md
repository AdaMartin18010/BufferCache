## 1. 概述与范围

部署决策链（自底向上）：

```text
引擎内前缀缓存（单实例，必开）
  → P/D 分离（池化，ISL 分布驱动）
  → 跨实例 KV 池（复用率 >30% 的多实例集群）
  → CPU/SSD 分层卸载（显存不足且 TTFT SLO 允许）
```

每一层的判断都有量化门槛（§2-§5），避免"为了架构而架构"。**P/D 分离的收益本质是 ISL（输入长度）与 OSL（输出长度）分布的函数**：DistServe（OSDI 2024）与 Splitwise（ISCA 2024）给出了理论基础——prefill 计算密集、decode 带宽密集，混合部署互相干扰（长 prompt 到达时 TTFT/TPOT 双飙升）。

## 2. 引擎内缓存配置基线

| 引擎 | 配置 | 说明 |
| ---- | ---- | ---- |
| vLLM V1 | `enable_prefix_caching=True`（默认开） | block 粒度前缀复用；`block_size` 16（默认）或 32 |
| SGLang | RadixAttention（默认开） | 基数树 + LRU 驱逐，系统提示/少样本场景复用率显著高于纯 hash 索引 |
| 两者共用 | `gpu_memory_utilization` 0.85-0.92 | KV 池占剩余显存；与权重/激活预算联动 |

**容量判据**（推导自 04.03.15 §3 的 KV 显存公式）：KV 池可缓存 token 数

$$N_{KV} = \frac{M_{pool} \times \eta}{2 \times L \times H \times d \times b}$$

其中 $M_{pool}$ 为 KV 池显存，$\eta$ 为分页利用率（PagedAttention 实测 ≥96%，推导自 vLLM SOSP'23），$L$ 层数、$H$ 注意力头数（GQA 用 KV 头数）、$d$ 头维、$b$ 精度字节（FP16=2）。MLA（DeepSeek 系）用低秩压缩后的 $d_c$ 替换 $H \times d$，可降一个数量级（DeepSeek-V2, 2024）。

## 3. P/D 分离部署路径

### 3.1 三条主流路径（2026-11）

| 路径 | 机制 | 状态 | 适用 |
| ---- | ---- | ---- | ---- |
| **SGLang 原生 disaggregation** | `--disaggregation-mode` 启动 prefill/decode 双池，GPU Staging Buffer 攒块传输 + Decode 侧 Radix Cache；KV 传输走 NCCL 或 NIXL | 0.5.12（2026-05-16）起一等公民；实测 1.8-2.4× 吞吐（Llama-3-70B） | 新部署首选，配置最简 |
| **vLLM V1 KV Connector** | `kv_transfer_config` 指定 connector（NIXL/Mooncake/LMCache），P/D 节点注册-读写 KV Block | 原生 API 成熟，生态 connector 最多 | 多厂商后端混搭 |
| **llm-d（K8s 编排层）** | "well-lit path" 文档化部署：router + prefill pods + decode pods，KV-aware 路由 | K8s 生产编排；与引擎解耦 | 已有 K8s 平台团队 |

### 3.2 容量配比

经验法则（无通用常数，须按负载推导）：

```text
prefill:decode 比例 ≈ (ISL_p99 / OSL_p99) × (decode 单 token 成本 / prefill 单 token 成本)
```

工程简化（来源：[DistServe OSDI'24](https://www.usenix.org/conference/osdi24/presentation/zhong-yinmin) 与社区实践，C 级经验）：对话型负载（ISL 1-4K, OSL 200-500）从 1:3 起步；长文档/Agent（ISL 8K+）从 1:1 起步，按 TTFT/TPOT SLO 双向压测收敛。SGLang 0.4 实测同卡数下解耦吞吐提升 1.8-2.4×（[Prompt20 2026-10](https://blog.prompt20.com/posts/disaggregated-inference/)，厂商环境 C 级）。

### 3.3 传输层

**NIXL（NVIDIA Inference Xfer Library）** 已成为 2026 年事实标准：RDMA/TP/以太网统一抽象，vLLM 与 TRT-LLM 均原生支持；Mooncake Transfer Engine 为跨实例池化场景的另一主流实现（支持 DRAM/NVMe 多介质）。

## 4. 跨实例 KV 池：Mooncake Store 与 LMCache

### 4.1 Mooncake 部署组件

```text
┌────────────┐   ┌──────────────┐   ┌────────────────┐
│ vLLM 实例A │──▶│ MooncakeStore │◀──│ vLLM 实例B/C... │
└────────────┘   │ （分布式KV池） │   └────────────────┘
                 └──────┬───────┘
                        ▼
              Transfer Engine（RDMA 为主）
```

- **集成方式**：vLLM `MooncakeConnector`（KV Connector 的一种实现）；官方集成数据：3.8× 吞吐、46× TTFT 降低（[vLLM 博客 2026-05-06](https://vllm.ai/blog/2026-05-06-mooncake-store)，厂商基准 C 级）。
- **部署要点**：Store 集群按 GPU 池划分；元数据服务独立部署；复用率 >30% 才值得跨实例化（否则传输开销 > 复用收益，推导自 04.03.15 §8.5 的准入判据）。
- **生态**：Mooncake 于 2026-02 加入 PyTorch 生态；Transfer Engine 已集成 TensorRT-LLM（2025-12）。

### 4.2 LMCache

- 定位：数据库式 KV 分层抽象，CPU/盘多级后端 + CacheBlend（前缀拼接）+ CacheGen（压缩传输）。
- 部署：与 vLLM 同机部署为 sidecar 进程或独立池；SageMaker HyperPod 有参考部署（2026-09）。
- 选型对照：Mooncake 强在跨实例 RDMA 池与生产验证；LMCache 强在多级后端与引擎解耦。

## 5. 分层卸载落地

判据（引用 04.03.15 §8.5，推导自重prefill 成本对比）：加载层 $i$ 的延迟 $t_{reload} = Size_{KV}/BW_i + t_{transfer}$ 必须小于重 prefill 成本。

| 层 | 介质 | 典型带宽 | 判据结论 |
| -- | ---- | -------- | -------- |
| L1 | CPU pinned DRAM | ~50-100 GB/s | 几乎总成立（10-100 倍余量） |
| L2 | 本地 NVMe | ~5-7 GB/s | 长前缀成立 |
| L3 | 远端/对象存储 | ~0.5-2 GB/s | 仅极高复用价值时成立 |

vLLM 落地配置：`--kv-offloading-size` + `--kv-offloading-backend native|lmcache`；或 `TieringOffloadingSpec` 声明 fs/obj/p2p 多级（[vLLM KV Offloading Connector, 2026-01-08](https://blog.vllm.ai/)）。

## 6. 观测指标与 SLO

| 指标 | 定义 | SLO 参考 |
| ---- | ---- | -------- |
| TTFT | 首 token 延迟 | 交互式 P50 <1s（分层命中时显著降低） |
| TPOT | 输出间隔 | P50 <50ms |
| 前缀复用率 | 命中 token 数 / 总输入 token | 系统提示型负载目标 >60% |
| KV 传输时延 | P→D / 池读写耗时 | P99 < 单 token decode 时间的 10% |
| 池命中率 | 跨实例池命中 / 请求数 | <30% 时重新评估池化价值 |

**先观测再架构**：per-request ISL/OSL/TTFT/TPOT 分位数与排队时间是 P/D 分离决策的输入，也是迁移后的验证基线（[agentnative 2026-07](https://www.agentnative.dev/compare/prefill-decode-disaggregation-vs-chunked-prefill)）。

## 7. 迁移方法论

1. **观测基线**（2 周）：采集 ISL/OSL/TTFT/TPOT/复用率分位数。
2. **引擎内优化先行**：确认前缀缓存开启、块大小与 KV 容量配置合理——多数团队止步于此即可。
3. **增量解耦**：P/D 池与混合部署并存，仅路由长 ISL 流量（如 ISL>8K）先行，收益最大、风险最小。
4. **池化扩展**：多实例复用率 >30% 再引入 Mooncake/LMCache。
5. **分层兜底**：显存水位告警后启用 CPU/NVMe 卸载，按 §5 判据设准入阈值。

## 9. 最小验证清单（GPU 环境）

```bash
# 1. 引擎内复用验证（单机单卡即可）
vllm serve <model> --enable-prefix-caching   # 观测日志 prefix cache hit rate
# 2. SGLang 解耦验证（双进程模拟双池）
python -m sglang.launch_server --model <model> --disaggregation-mode prefill --port 30000
python -m sglang.launch_server --model <model> --disaggregation-mode decode --port 30001
# 3. Mooncake（需 RDMA 环境或回退 TCP 模式）：按官方部署指南起 Store + 双 vLLM 实例

```
