## 1. 概述：LLM 缓存观测的三个特殊性

与通用缓存相比，LLM KV 缓存的观测有三个特殊性：

1. **价值单位是 token 而非请求**：节省的是 prefill 算力（token×FLOPs），命中率应按 token 计（[04.03.15](../04.03-行业应用场景/04.03.15-大模型推理缓存架构.md) §8.5 的准入判据也建立在 token 粒度）。
2. **层级多且异构**：GPU HBM ↔ CPU pinned ↔ NVMe ↔ 远端池，每层独立命中率与延迟，孤立看任何一层都会误判（分层准入的观测前提）。
3. **与调度器耦合**：缓存状态（空闲 block 数、排队长度）直接决定调度决策，观测必须暴露给调度器（闭环），不只是给人看。

## 2. 指标体系（四层）

| 层 | 指标 | 定义/计算 | 健康基线（经验起点，C 级） |
| -- | ---- | -------- | ------------------------ |
| 引擎内 | 前缀复用率 | 命中 token 数 / 总输入 token | 系统提示型负载 >60% |
| | KV 池利用率 | 已用 block / 总 block | 70-85%（过低浪费、过高触发抢占） |
| | 抢占率 | 被抢占请求数 / 总请求 | <1%（[04.03.15] 的 swapping/recompute 触发频率） |
| 分层 | 各层命中率 | 层 i 命中 / 到达层 i 的请求 | L2(CPU) >50% 才有继续分层价值 |
| | 换入换出速率 | bytes/s 每方向 | 与分层带宽预算对比（04.03.15 §8.5 判据） |
| | 换入延迟 P99 | 从换入开始到可解码 | < 单 token 解码时间的 10 倍 |
| 跨实例池 | 池命中率 | 跨实例命中 / 总请求 | >30%（低于此值池化收益为负，04.03.17 §4.1） |
| | KV 传输时延 | P→D / 池读写 P99 | < 单 token decode 的 10%（04.03.17 §6） |
| | 池内碎片 | 不可用 block / 总 block | <15% |
| SLO 层 | TTFT / TPOT | 首 token / 输出间隔 | 见 §3 |
| | 有效吞吐 | 输出 token/s（按请求计权） | 容量规划的锚（05.06.07 边界模型的 λ） |

**指标采集点**：vLLM `/metrics`（Prometheus exporter 内建，--enable-metrics）；SGLang 同类；Mooncake Store 自带池级指标。

## 3. SLO 定义方法

LLM 服务的 SLO 比传统服务多一个维度：**长度条件化**（同一系统对短请求和长请求的 TTFT 承诺不同）。

| SLO 维度 | 定义方法 | 示例 |
| -------- | -------- | ---- |
| TTFT（短输入 ≤1K） | P50/P99 分位数 | P50 <500ms，P99 <2s |
| TTFT（长输入 8K+） | 条件化分位 | P50 <1.5s（含 prefill 计算增长） |
| TPOT | 分位数 | P50 <50ms/token |
| 端到端（按输出长度） | 长度分桶 E2E | 1K 输出 P99 <60s |
| 可用性 | 成功请求 / 总请求（按错误类拆分） | >99.9%（排除限流拒绝） |

**错误预算消费**（SRE 方法，[Google SRE]）：预算 = 1 - SLO；长请求超时集中爆发是预算的主要消耗源——观测上要把"超时请求的输出长度分布"单独看（长请求超时占比高 → 考虑长度路由到独立池）。

## 4. 告警设计

| 告警 | 条件 | 级别 | 处置参考 |
| ---- | ---- | ---- | -------- |
| KVPoolExhaustionRisk | 池利用率 >90% 持续 5min | warning | 提前驱逐或扩容（07.09.01 内存水位伸缩） |
| PrefixReuseCollapse | 复用率 1h 下降 >20pp | warning | 检查负载漂移（会话断裂/提示词变更） |
| SwapThrashing | 换入速率 > 解码产出速率 持续 10min | critical | 容量不足或准入策略失效（04.03.15 §8.5 判据复核） |
| KVTransferLag | P→D 传输 P99 超预算 | critical | 网络/池瓶颈（04.03.17 §6 SLO） |
| TPOTDegradation | TPOT P99 > SLO×1.5 持续 15min | critical | 边界到达（05.06.07 拐点协议触发排查） |
| TTFTTailStorm | TTFT P99/P50 比 >10 持续 | warning | 排队或分层换入尖峰 |

**告警与自愈联动**：KVPoolExhaustionRisk 可作为 07.09.02 修复闭环的检测事件（自动触发分层扩容或驱逐策略切换，动作幂等性按 runbook 设计）。

## 5. 观测工具链

### 5.1 采集实操（vLLM 为例）

```bash
# 启动带指标导出的服务
vllm serve <model> --enable-metrics --port 8000
# Prometheus 抓取目标加入 :8000/metrics；关键指标名：
#   vllm:gpu_cache_usage_perc        KV 池利用率（§2 引擎内层）
#   vllm:prefix_cache_queries_total  前缀查询/命中计数（复用率=命中/查询）
#   vllm:time_to_first_token_seconds TTFT 直方图
#   vllm:time_per_output_token_seconds TPOT 直方图
# 复用率 PromQL（5min 窗）：
#   rate(vllm:prefix_cache_hits_total[5m]) / rate(vllm:prefix_cache_queries_total[5m])
```

### 5.2 面板配置（Grafana 核心三面板）

```yaml
# dashboard 片段（导入 Grafana 即用）
panels:
  - title: 前缀复用率
    expr: rate(vllm:prefix_cache_hits_total[5m]) / rate(vllm:prefix_cache_queries_total[5m])
    unit: percentunit; thresholds: [{value: 0.6, color: green}, {value: 0.3, color: yellow}]
  - title: KV 池利用率
    expr: vllm:gpu_cache_usage_perc
    unit: percentunit; thresholds: [{value: 0.9, color: red}, {value: 0.85, color: yellow}]
  - title: TTFT 分布
    expr: histogram_quantile(0.99, rate(vllm:time_to_first_token_seconds_bucket[5m]))
    unit: s; thresholds: [{value: 2, color: red}]
```

### 5.3 SLO 记录模板（错误预算台账）

```yaml
# slo.yaml —— 版本化管理，变更走 CR
slo: { name: llm-serving, window: 30d }
budget: 0.001                    # 1 - 99.9%
classes:
  - { name: ttft_short, metric: ttft_seconds{input_len<=1024}, target: p99<2s }
  - { name: ttft_long,  metric: ttft_seconds{input_len>8192}, target: p50<1.5s }
  - { name: tpot,       metric: tpot_seconds,                 target: p50<0.05s }
burn_alert: { fast: 14.4x, slow: 3x }   # 预算消耗速率告警（Google SRE 口径）
```


| 层 | 工具 | 说明 |
| -- | ---- | ---- |
| 引擎指标 | vLLM /metrics、SGLang metrics | Prometheus 抓取 |
| 池级指标 | Mooncake/LMCache 自带 exporter | 跨实例池命中率/传输 |
| 链路追踪 | OpenTelemetry（span: prefill/decode/transfer） | TTFT 分解到阶段（04.03.17 §6 的 T_detect 细化） |
| 面板 | Grafana：复用率/池水位/TTFT 分布三联 | 按 SLO 维度分面 |
| 日志 | 结构化请求日志（输入输出长度+缓存命中标记） | 事后分析与计费对账 |

## 6. 场景

1. **容量评审输入**：把"复用率 × 池利用率 × TPOT"三面板作为 07.05.04 式容量评审的 LLM 版输入。
2. **故障定位**：TPOT 劣化时按 §2 四层逐项排查（引擎→分层→池→SLO），与 07.07.03 的诊断决策树同构。
3. **成本归因**：按租户/业务的复用率分摊 GPU 成本（复用率高的业务单位 token 成本更低——缓存的金融化度量，[04.05](../../04-架构设计/04.05-成本优化/)）。
