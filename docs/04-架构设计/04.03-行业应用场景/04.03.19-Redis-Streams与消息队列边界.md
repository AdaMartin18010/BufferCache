## 1. 对比矩阵

| 维度 | Redis Streams | Kafka | RabbitMQ |
| ---- | ------------- | ----- | -------- |
| 吞吐（单机参考） | ~10 万 msg/s（C 级经验） | 百万级/s | 数万/s |
| 持久化 | AOF（内存为主，[03.02.06](../../03-Redis组件/03.02-持久化机制/03.02.06-持久化策略全局决策与成本模型.md)） | 磁盘顺序写（页缓存） | 磁盘（队列索引） |
| 保留 | 受 maxmemory 约束（XTRIM） | 按时间/大小（与消费无关） | ACK 后删除 |
| 消费模型 | 消费组（拉取+ACK+pending） | 分区+消费者组 | 队列+路由 |
| 回放 | 按 ID 任意重放（XRANGE） | 按 offset 重放 | 不支持（出队即删） |
| 延迟 | 毫秒级 | 毫秒-十毫秒 | 毫秒级 |
| 消息路由 | 无（key 即流） | topic+分区 | 灵活路由（direct/topic） |
| 生态 | Redis 客户端 | 完整生态（Connect/Schema Registry） | 企业集成 |

## 2. 决策树

```text
消息是否需要保留 >1 天且独立于消费？（审计/回放需求）
├─ 是 → Kafka（Streams 的 trimming 与内存约束不适合作系统记录）
└─ 否 → 吞吐需求 >10 万/s 或需跨团队数据契约？
    ├─ 是 → Kafka
    └─ 否 → 已在 Redis 生态 / 延迟敏感 / 轻量任务队列？
        ├─ 是 → Streams（一个组件两个用途，运维面最小）
        └─ 否 → 评估 RabbitMQ（复杂路由）或 Kafka（长期演进）
```

**Streams 甜点区**（B 级机制推导 + C 级经验）：延迟敏感的异步任务（<100ms 端到端）、可回放但保留期短（小时-天级）、消费组数量少（<10）、吞吐 <10 万/s。**出甜点区任何一条** → Kafka。

## 3. Streams 处理管道设计

at-least-once 标准管道（消费组语义，B 级官方机制）：

```
XADD 生产 → 消费者 XREADGROUP（> 新消息 / 0 历史）→ 处理 → XACK
                                    ↓ 崩溃
              pending list 滞留 → 恢复后 XAUTOCLAIM 认领（转移闲置消息）→ 处理 → XACK
```

| 设计点 | 推荐 | 理由 |
| ------ | ---- | ---- |
| ACK 时机 | 处理成功后（先处理后 ACK） | at-least-once：崩溃留 pending，由认领重放 |
| 幂等 | 消费端幂等（消息 ID 去重表） | at-least-once 必然重复（认领/重投） |
| 认领策略 | `XAUTOCLAIM`（7.0+，原子认领闲置） | 替代旧版 XCLAIM 遍历（O(N) 扫描） |
| 死信 | pending 重试 N 次后 XADD 到死信流 | 无原生死信，应用层实现 |
| 容量 | `MAXLEN ~ N`（近似修剪）+ 监控 | 防内存膨胀；~ 近似避免每消息精确裁剪的额外开销 |

**背压**：消费者慢 → pending 增长 → 以 `XPENDING` 的消费组滞后（entries-read - last-delivered）作为伸缩信号（[07.09.01 KEDA 触发器](../../07-运维与部署/07.09-弹性伸缩与自愈/07.09.01-自动伸缩实践.md) §4 已给配置示例）。

## 4. Streams 的机制边界

1. **无分区并行消费组内分片**：消费组内消息按 ID 轮询分发，不能像 Kafka partition 按 key 保序并行——需要 key 级有序时按 key 分多个流（应用层分片）。
2. **内存硬约束**：Streams 本质是内存数据结构（[03.01.08](../../03-Redis组件/03.01-核心数据结构/03.01.08-Stream流数据结构.md)），AOF everysec 下宕机丢 1s；**不可当持久记录系统**。
3. **集群多 key 限制**：消费者组相关命令跨 slot 受限（hash tag 共置，[01.03.05 §5](../../01-理论基础/01.03-分布式缓存算法/01.03.05-数据分片数学与再平衡模型.md)）。
4. **pub/sub 对比**：pub/sub 无持久无缓冲（[03.06.06 §3](../../03-Redis组件/03.06-网络通信/03.06.06-客户端缓冲与背压治理.md)）；Streams 有持久+消费组——**"消息不能丢"是 Streams 与 pub/sub 的分界线**。

## 5. 迁移路径

Streams → Kafka 的渐进式（C 级工程路径）：

1. 双写期：应用同时 XADD 与 Kafka produce（消费仍读 Streams）。
2. 影子消费：Kafka 消费者上线只比对不落库（对账 [04.04.11](../../04-架构设计/04.04-缓存问题与治理/04.04.11-缓存数据对账与校验.md) 思路）。
3. 切读：消费切 Kafka，Streams 保留只读窗口期（回放保险）。
4. 下线：Streams key 过期自然清理。
