# 04.04.08 缓存失效传播与一致性链路

> 缓存失效（失效缓存数据使其与数据源一致）是 Cache-Aside 体系的正确性核心。本文把失效从"删缓存一个动作"展开为**传播机制的系统论证**：三条失效链路的时序与窗口、失效风暴的排队模型、多级缓存的级联时序，并与 [TC-BENCH-003](../../../Testing/cases/02-形式化与基准/TC-BENCH-003-缓存一致性竞态验证.md) 的可执行实验互相印证。

## 1. 概述：失效的三条链路

| 链路 | 机制 | 一致性窗口 | 存储/改造代价 |
| ---- | ---- | ---------- | ------------ |
| L1 主动删除 | 写 DB 后删缓存（可延迟双删） | 删除失败+并发回填的竞态窗口（~ms-s，TTL-BENCH-003 实测） | 无额外存储；删除可能失败 |
| L2 CDC 订阅 | binlog（Debezium/Canal）→ 消费端删缓存 | binlog 产生到消费延迟（~100ms-s） | 引入消息队列与订阅服务 |
| L3 版本号/逻辑过期 | value 带版本，读时比对 DB 版本 | 无窗口（读到旧版本即回源） | 存储膨胀 + 每次读比对成本 |

## 2. 链路时序与一致性窗口

### 2.1 L1 主动删除的竞态（TC-BENCH-003 的时序版）

```
线程A 写DB(v2) ──→ 删缓存（成功/失败）
线程B          读缓存miss ──→ 读DB(v2) ──→ 回填v2        ← 正常
线程C  读缓存(v1) ←──────── 在A写DB后、删缓存前回填了v1  ← 不一致窗口
```

窗口 = "DB 已更新"到"缓存旧值被删除或覆盖"的时长。延迟双删的第二次删除覆盖"第一次失败后并发读回填"的剩余竞态——但**仍留理论窗口**（第二次删除后还有读回填旧值的可能，概率随 TTL 兜底归零）。可执行证据：TC-BENCH-003 实测 B（TTL）窗口上界 = TTL，C（双删）窗口 ≈ 删除延迟。

### 2.2 L2 CDC 的端到端窗口

$$T_{window}^{CDC} = T_{db\_commit} + T_{binlog} + T_{mq} + T_{consume} + T_{del}$$

典型量级（经验值，C 级）：MySQL binlog flush ~ms + Kafka 端到端 ~10-100ms + 消费处理 ~ms → **总窗口 100ms-1s**。比 L1 的竞态窗口大，但**无删除失败模式**（至少一次投递，消费幂等即可）。

### 2.3 L3 版本号的零窗口代价

读路径：取缓存 `(v, data)` → 比对 DB 当前版本（或版本缓存）→ 旧则回源。一致性最强，但每次读多一次版本比对（或维护版本缓存的二级一致性问题——版本缓存自身又需要失效，递归成本常被低估）。

## 3. 失效风暴：排队模型与互斥重建

热点 key 失效瞬间，$Q$ 个并发请求同时 miss 回源（dogpile）。无防护时回源并发 = Q；互斥重建（单飞 singleflight）时仅 1 个线程回源，其余等待。

等待队列按 M/M/1 近似（Kleinrock，B 级）：回源服务率 $\mu$，请求到达率 $\lambda$（=Q 集中在窗口内），平均等待：

$$W = \frac{1}{\mu - \lambda} \quad (\lambda < \mu)$$

**拐点特性**：$\lambda \to \mu$ 时等待发散——失效风暴的自我放大机制。工程防护（与 [04.04.03 缓存击穿](04.04.03-缓存击穿.md) 同一族）：互斥锁 + 逻辑过期（等待线程返回旧值而非阻塞）+ 请求合并，把 $\lambda$ 有效值压到 $\mu/2$ 以下（C 级经验水位）。

## 4. 多级缓存的级联失效

L1（本地，如 Caffeine）+ L2（Redis）两级时，失效必须级联：

```
DB 更新 → 删 L2 → 广播失效消息 → 各实例删 L1
              ↑ 若删 L2 成功但广播丢失：L1 旧值滞留至本地 TTL
```

级联时序要点：
- **L1 的 TTL 是级联失效的最终保险**（本地 TTL 应显著短于 L2，如 L1 60s vs L2 6h）。
- 失效广播（Redis pub/sub 或自定义消息）至少一次语义，L1 消费需幂等。
- **级联失效风暴**：L2 批量失效（如大范围数据变更）→ 广播洪峰 → L1 集中回源 L2 → L2 集中回源 DB。缓解：失效消息抖动 + 分层随机回源（每个 L1 实例延迟随机 0-τ 后再回源，摊平 λ）。

## 5. 三条链路选型决策

| 场景 | 推荐 | 理由 |
| ---- | ---- | ---- |
| 一般读多写少 | L1 + TTL 兜底 | 成本最低，窗口可容忍 |
| 写后读强一致（库存） | L3 版本号 或 写穿透 | 窗口不可接受 |
| 多服务共享数据变更频繁 | L2 CDC | 删除失败模式被消除，跨服务一致 |
| 多级缓存 | L1+L2 级联（L2 用 L1 链路，L1 靠 TTL+广播） | 平衡窗口与成本 |

## 6. 场景

1. **库存扣减**：L3 版本号 + 写穿透；任何窗口不可接受。
2. ** feed 内容更新**：L2 CDC（用户服务多写方统一走 binlog）；TTL 兜底。
3. **配置类缓存**：L1 长 TTL + 主动广播失效（变更低频，广播成本可忽略）。
