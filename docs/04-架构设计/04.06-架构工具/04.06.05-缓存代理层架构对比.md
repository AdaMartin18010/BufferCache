## 1. 三分架构

```text
A. 客户端直连 Cluster：客户端持有拓扑，MOVED/ASK 自适应（现代客户端标配）
B. 代理层分片：客户端只连代理，代理维护分片拓扑（Twemproxy/Codis/Envoy）
C. 代理层能力扩展：代理层附加功能（Envoy 过滤链：熔断/限流/可观测）
```

**本质**：代理层用"一跳网络转发 + 中心化拓扑管理"换取"客户端零改造"；直连用"客户端复杂度"换取"少一跳、少一个故障点"。

## 2. 历史方案谱系

| 方案 | 年代 | 架构 | 分片机制 | 迁移能力 | 状态（2026） |
| ---- | ---- | ---- | -------- | -------- | ------------ |
| Twemproxy（nutcracker） | 2012 | 无状态代理层，客户端连代理 | 一致性哈希（静态配置） | **不支持在线迁移**（改配置重启） | 维护态（Twitter 弃用已久） |
| Codis | 2014-2018 | 代理层 + Dashboard + 元数据（ZK/etcd） | 预分片 1024 slot | 支持在线迁移（slot 级） | 停更（被 Redis Cluster 取代） |
| Redis Cluster | 2015+ | 无中心，Gossip | 16384 slot | 原生 reshard（[07.09.04](../../07-运维与部署/07.09-弹性伸缩与自愈/07.09.04-分片级弹性伸缩与分区迁移.md)） | 主流 |

**历史教训**（C 级工程归纳）：Twemproxy 的静态分片在数据增长后无法平滑迁移，是 Codis 出现的动机；Codis 证明了"代理层 + 中心元数据"可行，但其复杂度（三个组件）最终被 Redis Cluster 的无中心设计取代。**代理层方案的兴衰本质是"分片拓扑管理权放哪"的探索史**。

## 3. 现代形态：Envoy Redis

Envoy 的 Redis 代理（RedisProxy filter）给代理层带来新生命——不在分片上竞争（转发逻辑仍靠 Cluster 感知或简单哈希），而在**横切能力**上：

| 能力 | 说明 | 与直连对比的价值 |
| ---- | ---- | ---------------- |
| 连接收敛 | 代理到后端的连接池化，客户端连接数无关 | 10 万 Pod 连 Redis 的连接风暴治理 |
| 熔断/限流 | Envoy 过滤链原生能力 | 客户端无需统一实现（[03.06.07](../../03-Redis组件/03.06-网络通信/03.06.07-客户端连接与重试行为矩阵.md) 的客户端治理下沉到代理） |
| 可观测 | 统一 metrics/tracing 出口 | 多语言客户端的观测标准化 |
| 多集群路由 | 按 key 前缀路由到不同后端集群 | 灰度/隔离（影子集群、[04.03.19 多活](../../07-运维与部署/07.04-故障处理/07.04.04-跨机房多活缓存设计.md) 的流量分配） |

## 4. 决策矩阵

| 场景 | 推荐 | 理由 |
| ---- | ---- | ---- |
| 新系统 + 现代客户端 | **直连 Cluster** | 少一跳、少故障点；客户端库（Lettuce/go-redis 6.x+）已成熟 |
| 遗留客户端无 Cluster 支持 | 代理层（Envoy） | 改造客户端成本高 |
| 连接数爆炸（Serverless/高 Pod 密度） | Envoy 连接收敛 | 后端连接数 = 代理数 × 池大小，与客户端规模解耦 |
| 统一治理（熔断/限流/审计） | Envoy 过滤链 | 横切能力一次实现全客户端受益 |
| 需要在线迁移且客户端旧 | Codis 式（历史方案，现多用 Cluster + 代理过渡） | 现代等价：Cluster 渐进迁移 + 代理双写过渡 |

## 5. 代理层的固有局限

1. **性能损耗**：一跳网络转发，P99 增加 0.1-0.5ms（同 AZ，C 级经验值）+ 代理自身 CPU（Envoy 单核 ~5-10 万 Redis QPS）。
2. **多 key 命令**：跨分片 MULTI/事务/Lua 经代理层无法透明支持（Twemproxy 直接不支持；Envoy 需 Cluster 感知模式 + 限制）。
3. **新特性滞后**：Redis 新命令/协议（RESP3、Function、Sharded pubsub）在代理层的支持晚于客户端。
4. **故障面**：代理层本身是新的故障域与容量瓶颈（横向扩展代理=又一套集群管理）。

## 6. 实测补充（2026-11-17，redis-lab 环境）

代理层开销的本项目实测锚点（Docker Desktop/Windows，C 级环境）：

| 路径 | RTT（redis-cli PING） |
| ---- | -------------------- |
| 直连容器（host 映射端口） | ~1-2ms（含 Docker NAT） |
| 经 toxiproxy 代理（同主机） | +0.1-0.3ms（代理转发开销） |

结论与本章 §5 的量级一致：同 AZ 代理一跳为亚毫秒级；跨 AZ 或代理高负载时才是主要成本。**生产评估应以自家链路 toxiproxy 实测为准**（复用 TC-CLUS-007 环境，latency toxic 设 0 即得纯代理开销）。

## 7. 场景

1. **Service Mesh 环境**：Envoy 已是基础设施，Redis 代理是顺手的能力扩展（连接收敛 + 熔断）。
2. **遗留系统渐进改造**：旧客户端先经代理接 Cluster，新服务逐步直连，过渡期并存。
3. **多租户平台**：代理层做 key 前缀路由 + 配额（Envoy rate limit），租户隔离不下沉到客户端。
