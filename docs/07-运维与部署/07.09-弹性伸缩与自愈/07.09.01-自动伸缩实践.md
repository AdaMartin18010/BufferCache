# 07.09.01 自动伸缩实践

> 自动伸缩（Autoscaling）让缓存系统的容量跟随负载自动调整：峰值不降级、谷值不浪费。本文覆盖 K8s 伸缩工具全景（HPA/VPA/KEDA/Karpenter）、缓存特有的内存水位驱动伸缩、以及伸缩决策中的延迟账与冷却设计。

## 1. 概述

伸缩不是调一个"负载旋钮"，而是**三个层面各自独立的控制回路**，选错层面工具正确也解决不了问题（2026 年社区共识，来源见 §10）：

```text
流量上涨
  → L1 Pod 层：HPA/KEDA 加副本（秒-十秒级）
  → L2 节点层：Karpenter/CA 加节点（几十秒-分钟级）
  → L3 集群/分片层：Redis Cluster reshard / 云实例升配（分钟级，常需人工门禁）
```

2026 年关键事实：生产集群平均 CPU 利用率仅约 8%（Cast AI 2026 报告，C 级）——伸缩在跑但没切掉闲置容量；多数团队的首要收益来自**缩容速度**（scale-down 延迟与冷却窗口）而非扩容速度。

## 2. 伸缩的三个层面

| 层面 | 对象 | 工具 | 时间尺度 | 决策输入 |
| ---- | ---- | ---- | -------- | -------- |
| L1 Pod | 副本数 | HPA / KEDA | 15s-2min | CPU/内存/自定义/外部指标、事件 |
| L1 Pod | 单 Pod 规格 | VPA | 分钟级（需重启） | 历史用量 P95 |
| L2 节点 | 节点数与型号 | Karpenter / Cluster Autoscaler | 40s-5min | Pending Pod、利用率 |
| L3 集群 | 分片/实例 | redis-cli --cluster reshard、云控制台/API | 分钟-小时 | 分片内存/QPS 水位 |

## 3. HPA：水平 Pod 伸缩

### 3.1 工作机制

```text
指标采集（kubelet/cadvisor，15s 窗口）
  → HPA 控制循环（默认 15s 一次）
  → 期望副本数 = ceil(当前副本 × 当前指标值 / 目标值)
  → 受 min/max 与伸缩速率限制约束 → 更新 Deployment/StatefulSet
```

### 3.2 指标类型（autoscaling/v2）

| 指标类型 | 来源 | 缓存场景示例 |
| -------- | ---- | ------------ |
| Resource | CPU/内存 | 缓存代理 sidecar 按 CPU 伸缩 |
| Pods（自定义） | 应用暴露的 metrics | 每秒操作数、连接数 |
| Object | 任意 K8s 对象指标 | 每 Pod 网络吞吐 |
| External | 集群外指标（Prometheus Adapter） | **Redis 内存用量、QPS**（见 §6） |

### 3.3 关键参数

```yaml
behavior:                 # 伸缩行为（防抖动核心）
  scaleDown:
    stabilizationWindowSeconds: 300   # 缩容稳定窗口：取窗口内最高期望值
    policies: [{type: Percent, value: 50, periodSeconds: 60}]  # 每分钟最多缩 50%
  scaleUp:
    stabilizationWindowSeconds: 0
    policies: [{type: Pods, value: 4, periodSeconds: 60}]     # 每分钟最多加 4 个
```

- **缩容稳定窗口**是利用率杀手：窗口太短会在流量抖动后过度缩容再被迫扩容（flapping）；太长则闲置成本。
- 2026 年趋势：HPA 从 K8s 1.37 起原生支持缩到 0（object/external 指标），此前 scale-to-zero 需 KEDA。

## 4. KEDA：事件驱动伸缩

KEDA（CNCF Graduated）在 HPA 之上提供 **70+ 事件源 scaler** 与 **scale-to-zero**（来源：CAST AI / Control Plane 2026 对比）：

```yaml
# 缓存消费者按 Redis Stream 消费者滞后伸缩（KEDA ScaledObject 示意）
triggers:
  - type: redis-streams
    metadata:
      stream: mystream
      consumerGroup: mygroup
      pendingEntriesCount: "5"     # XINFO GROUPS 的 pending 数超阈值即扩容
      lagCount: "10"               # 或按 entries-read - last-delivered 滞后量
```

| 能力 | HPA | KEDA |
| ---- | --- | ---- |
| 指标来源 | 资源/自定义/外部 | 70+ 事件源（队列深度、Kafka lag、cron、Prometheus 查询） |
| Scale-to-zero | 1.37+ 才支持（部分指标） | 原生支持 |
| 适用 | 稳态 Web/服务负载 | 批处理、队列消费、潮汐/季节性负载 |

**选型经验**（2026 社区基准，C 级）：纯 CPU/内存用 HPA 足够；事件驱动（Redis 队列、Kafka 消费）用 KEDA；两者可共存于不同工作负载，勿对同一工作负载叠加。

## 5. VPA 与节点伸缩（Karpenter/Cluster Autoscaler）

- **VPA**：调 Pod 的 requests/limits。生产建议先跑 **recommendation 模式**（只给建议）观察 1-2 周再开自动更新；自动更新触发 Pod 重建，与 HPA **不可基于同一指标并用**（典型组合：HPA 按 QPS 扩副本 + VPA 只调内存 requests）。
- **Karpenter vs Cluster Autoscaler**（2026 对比，来源见 §10）：
  - Karpenter（AWS 起家，Sandbox）：按 Pending Pod 批次直接选最优实例型号、bin-packing 更紧、**consolidation**（把利用率低的大节点换成放得下全部 Pod 的小节点）带来持续成本收益、spot 中断前预建替代节点并优雅排空。
  - Cluster Autoscaler：预定义节点组扩容，云无关性最好（GKE/AKS/裸金属），最经得起验证。
  - 迁移共识（LabHub 2026）：AWS 上 CA→Karpenter 是成本收益最大的单项迁移之一。

## 6. 缓存特有：内存水位驱动伸缩

缓存系统的伸缩信号不是 CPU 而是**内存水位**——CPU 可被打满而数据无恙，内存打满则直接驱逐/报错：

```text
Redis 内存指标（redis_exporter: redis_memory_used_bytes / maxmemory）
  → Prometheus Adapter → External Metric (memory_utilization)
  → HPA 扩缓存代理/分片副本
  或 → 告警 + Cluster reshard（L3，人工门禁）
```

**双轨策略**：
1. **读路径**（代理/sidecar）：内存或 QPS 水位直接 HPA/KEDA，无状态可随时扩缩。
2. **数据路径**（Redis Cluster 分片）：扩容 = 新增主分片 + reshard 迁槽（见 [07.05.01](../07.05-集群管理/07.05.01-集群部署实践.md)），缩容需谨慎（迁槽期间双写窗口），通常**只自动扩、人工审缩**。

云托管缓存（ElastiCache Serverless / Memorystore cluster 层）已内置内存驱动自动伸缩，自建集群用上述双轨补齐。

## 7. 性能分析：伸缩延迟账

一次完整扩容的总延迟（推导自各组件默认周期，B 级）：

$$T_{scale} = T_{metric}(15s) + T_{hpa}(15s) + T_{sched}(秒级) + T_{pull}(镜像, 30s-数分) + T_{warm}(缓存预热)$$

- 无预热缓存的扩容等于**冷启动**：新副本 miss 风暴回源。缓解：就绪探针延迟接入（`readinessProbe` 通过前不接流量）+ 请求级影子预热 + 回源请求合并（[04.04.03](../../04-架构设计/04.04-缓存问题与治理/04.04.03-缓存击穿.md)）。
- 缩容延迟账：`stabilizationWindowSeconds`（默认 300s）+ Pod 终止宽限（`terminationGracePeriodSeconds`）+ 有状态缓存的**数据再平衡时间**（Cluster 迁槽分钟级）。
- Flapping 防护：扩容阈值滞回（扩 70% 缩 30%，非对称目标）、最小副本数兜底、冷却窗口。

## 8. 典型场景

1. **大促弹性（电商）**：KEDA cron scaler 预热扩容 + HPA 水位兜底；缓存代理层随 QPS 扩，数据层提前 reshard 到位（L3 前置，不临场扩）。
2. **消息队列型缓存消费者**：KEDA Redis Streams lag scaler，夜间缩到 0，早高峰按滞后量自动拉起。
3. **LLM 推理集群**：vLLM 实例按 KV 池水位（`gpu_memory_utilization`）+ 队列深度伸缩；P/D 分离后 prefill/decode 池独立伸缩（[04.03.17](../../04-架构设计/04.03-行业应用场景/04.03.17-大模型推理缓存部署实践.md) §3.2 配比）。
4. **成本敏感批处理**：Karpenter consolidation + spot 节点池，周末自动缩容到最小规模。
