# 07.09.02 自愈机制实践

> 自愈（Self-Healing）是系统在无需人工介入下检测故障并自动恢复的能力。本文建立缓存系统的自愈五层模型，详解 K8s 探针与重启原语、缓存层特有自愈机制，以及"检测→决策→执行→验证→学习"的修复闭环设计。

## 1. 概述与五层模型

```text
L1 进程层   进程崩溃 → supervisor 自动重启（秒级）
L2 Pod 层   容器/Pod 故障 → K8s 重启策略 + 探针重建（十秒级）
L3 实例层   节点实例宕机 → Sentinel/Cluster 自动故障转移（秒-十秒级，07.05）
L4 应用层   依赖故障 → 熔断/降级/重试隔离（毫秒-秒级，02.06）
L5 数据中心 机房级故障 → 多活切换（分钟级，预案驱动，07.04）
```

层级越高恢复代价越大：**下层自愈是上层自愈的前提**——L1/L2 失效的实例靠 L3 转移，L3 失效的集群靠 L5 兜底。研究综述表明 K8s 自愈机制可将事件响应时间缩短约一半（ISTC 2026 / IJSET 2026 案例，C 级）。

自愈有效性的两个前提（ISTC 2026 实践结论）：**实时可观测**（无 Prometheus/Grafana 级指标则无法证明自愈生效）与**处置动作幂等**（同一修复动作重复执行不产生副作用）。

## 2. K8s 自愈原语

### 2.1 探针三件套（执行顺序：startup → readiness/liveness）

| 探针 | 作用 | 失败后果 | 设计要点 |
| ---- | ---- | -------- | -------- |
| startupProbe | 探测慢启动应用是否就绪 | 重启容器 | 先执行；成功前屏蔽另两个探针，防慢启动被 liveness 误杀 |
| readinessProbe | 是否可接流量 | 从 Service Endpoints 摘除（不重启） | 缓存预热完成前保持 NotReady，防冷启动 miss 风暴 |
| livenessProbe | 是否死锁/僵死 | 重启容器 | 必须真死才失败——依赖短暂超时不应触发重启循环 |

Redis 实例探针实践：

```yaml
livenessProbe:
  exec: { command: ["redis-cli", "-a", "$(REDIS_PASSWORD)", "ping"] }
  periodSeconds: 10
  timeoutSeconds: 3
  failureThreshold: 5        # 50s 无响应才判死，避免慢命令误杀
readinessProbe:
  exec: { command: ["redis-cli", "-a", "$(REDIS_PASSWORD)", "ping"] }
  periodSeconds: 5
  failureThreshold: 2
startupProbe:
  exec: { command: ["redis-cli", "-a", "$(REDIS_PASSWORD)", "ping"] }
  periodSeconds: 5
  failureThreshold: 30       # 最长容忍 150s 启动（大实例 RDB 加载）
```

### 2.2 重启与调度原语

- `restartPolicy: Always/OnFailure`：Pod 内容器统一重启策略。
- `terminationGracePeriodSeconds`：终止宽限，缓存节点需足够完成 RDB 触发/复制偏移同步，大实例给 60-300s。
- `PodDisruptionBudget`：自愈与维护的冲突面——驱逐（节点升级/缩容）时保证最少存活副本，防止"自愿中断"叠加"非自愿故障"击穿可用性。
- 污点与隔离：故障节点自动打 `NoSchedule` 污点（node-problem-detector + draino），防止 Pod 反复调度回故障节点形成重启循环。

### 2.3 重启风暴防护

探针配置不当会引发重启循环（crashloop），三条防线：
1. `startupProbe` 兜底慢启动；
2. 指数退避重启（K8s 默认 crashloop 退避 10s→5min 上限）；
3. 全局限流：Pod 重启率告警（`kube_pod_container_status_restarts_total` 突增）联动熔断部署。

## 3. 缓存层自愈机制

| 故障 | 自愈机制 | 恢复时间 | 关键配置 |
| ---- | -------- | -------- | -------- |
| 主实例宕机 | Sentinel/Cluster 自动转移（L3） | 10-40s（实测见 [07.04.03](../07.04-故障处理/07.04.03-应急预案.md) 演练记录） | quorum、down-after |
| 从实例宕机/断链 | 自动重连 + 部分重同步（PSYNC2） | 秒-分钟 | repl-backlog-size、repl-timeout |
| 内存碎片率过高 | `activedefrag yes` 自动整理 | 后台渐进 | active-defrag-threshold-lower/upper |
| AOF 膨胀 | `auto-aof-rewrite-percentage` 自动重写 | 后台 | 混合持久化开 |
| 热 key 打满单分片 | 客户端本地缓存兜底 + 热 key 副本扩散（应用层） | 即时 | 见 04.04.04 |
| 慢查询堆积 | `slowlog` 监控 + 超时命令熔断（应用层） | 即时 | slowlog-log-slower-than |
| 脑裂（双主） | min-replicas-to-write 拒写 + Sentinel 仲裁 epoch | 秒级 | min-replicas、quorum |

**数据自愈特例**：副本同步中断后的恢复路径选择——backlog 内 → 部分重同步（快）；backlog 外 → 全量 RDB 重传（分钟级，网络抖动大时反复全量是常见事故源，07.05.02 有专门调优）。

## 4. 自动修复闭环设计

高级自愈不止于"重启"，而是 runbook 自动化（AIOps 的工程化形态）：

```text
检测 Detection     告警/探针/异常检测（07.03 指标 + 静态阈值/动态基线）
  → 决策 Decision    runbook 匹配（哪种故障→哪个修复动作），人工审批分级
  → 执行 Action      重启/隔离/转移/扩容/降级（动作必须幂等）
  → 验证 Verification 健康检查 + 指标回归（不能只"执行了"，要"恢复了"）
  → 学习 Learning    复盘归档为新 runbook / 新告警规则 / 新演练场景
```

工程落地要点：
- **动作幂等**：`RESTART` 前先查状态；`RESHARD` 前校验槽平衡度；所有动作可重入。
- **人工门禁分级**：L1-L2 自动执行；L3 自动执行 + 事后审计；L4-L5 自动建议 + 人工确认。
- **修复半径（blast radius）**：一次修复动作影响的面必须小于故障本身——单实例重启优于整批重启。
- 与 04.06.04（AI 驱动优化）的关系：AI 用于异常检测与根因建议，**执行层保持确定性 runbook**（可审计、可回放）。

## 5. 性能分析：恢复时间账

各层自愈的 RTO 预算（与 07.04.03 演练登记一致）：

| 层 | 检测时间 | 恢复时间 | 总 RTO 目标 |
| -- | -------- | -------- | ----------- |
| L1 进程 | 秒级（supervisor） | 秒级 | <30s |
| L2 Pod | 10-50s（探针周期×阈值） | 调度+启动 10-60s | <2min |
| L3 实例 | 5-15s（主观下线）+选举 | 转移 10-30s | <40s（实测 Sentinel ~10s、Cluster 25-40s） |
| L4 应用 | 毫秒（熔断器半开探测） | 秒级 | <5s |
| L5 机房 | 分钟（健康检查收敛） | DNS/流量切换分钟级 | <15min |

**MTTR 构成**（SRE 通用模型）：$MTTR = T_{detect} + T_{diagnose} + T_{repair} + T_{verify}$。自愈压缩的是 $T_{repair}$；可观测性压缩 $T_{detect/diagnose}$；演练（07.09.03）压缩的是**整个分布的尾部长度**。

## 6. 典型场景

1. **缓存 Pod OOM**：L2 探针检出 → 重启 → readiness 等待预热 → 接入；同时触发内存水位告警反向驱动扩容（07.09.01 §6）。
2. **主实例僵死（进程在但不响应）**：liveness 探针 50s 检出重启；Sentinel 5s 检出转移——**双通道自愈**，转移先于重启完成，客户端无感。
3. **AOF 磁盘写满**：磁盘水位告警 → runbook 自动清理旧 AOF 备份 + 触发重写 + 通知扩容磁盘。
4. **机房断电演练**：L5 预案驱动，GSLB 切换 + 缓存集群异地只读降级。
