## 1. 概述与原则

混沌工程（Chaos Engineering）通过在生产近似环境中**主动注入故障**，验证系统的韧性假设。四条原则（混沌工程原则社区共识，B 级）：

1. **建立稳态假设**：定义"系统正常"的可量化表征（如 miss ratio <2%、P99 <20ms），而非"没有报错"。
2. **模拟真实世界事件**：优先注入生产中发生过的故障形态（断网、实例宕机、磁盘写满、时钟偏移）。
3. **生产环境运行**：blast radius 可控的前提下越接近生产越有价值；从预发逐步晋级。
4. **持续自动化**：演练不是一次性项目，而是 CI/CD 化的定期流水线（本项目的 [Testing 集群用例](../../../Testing/cases/04-集群/) 即最小形态）。

与测试的区别：传统测试验证**功能正确**，混沌工程验证**故障下的行为性质**（恢复时间、降级路径、无级联失效）。

## 2. 稳态假设与实验设计

### 2.1 稳态指标（缓存系统示例）

| 指标 | 稳态假设 | 数据来源 |
| ---- | -------- | -------- |
| 命中率 | ≥ 基线 -1%（故障注入期间允许轻微下降） | redis_exporter / 应用埋点 |
| P99 延迟 | ≤ 基线 ×1.5 | APM（07.06.03） |
| 错误率 | <0.1%（failover 窗口除外） | 网关/客户端指标 |
| 恢复时间 | 自动恢复 ≤ 各层 RTO（07.09.02 §5） | 演练计时 |
| 数据一致性 | 主从切换后无脏读/双写 | 校验和抽查 |

### 2.2 实验设计模板

```text
假设：杀掉任一 Redis Cluster 主节点，60 秒内自动转移且命中率下降 <2%
爆炸半径：预发集群单节点（→ 生产单节点 → 生产 AZ）
注入：pod-kill / node-kill（定时 1 次）
观测：07.03 指标面板 + 本实验对照组（未注入时段基线）
中止条件：命中率下降 >5% 持续 60s / 人工一键停止（Chaos Mesh 支持一键终止）
结论：通过/失败 + 差距归因 + 新增防护项
```

## 3. 工具链：Chaos Mesh 实践

Chaos Mesh（CNCF，K8s 原生）以 CRD 描述实验，主要故障类型与缓存场景映射：

| 故障类型 | CRD | 缓存验证场景 |
| -------- | --- | ------------ |
| PodChaos | pod-kill / pod-failure / container-kill | 主从实例宕机（L3 自愈计时，衔接 TC-CLUS-003/004） |
| NetworkChaos | delay / loss / partition / duplicate | 跨 AZ 复制延迟、脑裂分区、Sentinel 通信隔离 |
| StressChaos | cpu / memory / io | 热 key CPU 打满、内存压力触发驱逐 |
| IOChaos | latency / errno / mixed | AOF 磁盘抖动、fsync 变慢 |
| TimeChaos | time-offset | 时钟漂移下 Sentinel 选举与 TLS 证书校验 |
| KernelChaos | 内核故障注入 | 页回收压力（配合 MGLRU 观测） |
| DNSChaos | dns-error / random | 客户端集群发现失败降级 |

最小实验示例（NetworkChaos 延迟注入）：

```yaml
apiVersion: chaos-mesh.org/v1alpha1
kind: NetworkChaos
metadata:
  name: redis-replica-delay
  namespace: chaos-testing
spec:
  action: delay
  mode: one                       # 爆炸半径：单个 Pod
  selector:
    labelSelectors:
      app.kubernetes.io/name: redis
      role: replica
  delay:
    latency: 100ms
    correlation: "80"             # 80% 相关性（非完全随机，更接近真实抖动）
  duration: 5m
```

**安全护栏**：生产演练必须配置 `abortCondition`（Chaos Mesh Dashboard 一键中止）、演练窗口（低峰）、通知（值班群机器人）、自动回滚（实验 CRD 设置 duration 自动清理）。

## 4. 缓存系统专项故障场景

按故障域组织的场景清单（★ 为建议首批，可用 Testing/fixtures/redis-lab 执行）：

| 域 | 场景 | 验证的韧性 |
| -- | ---- | ---------- |
| 实例 | ★ 主实例 kill/pause | Sentinel/Cluster 转移 RTO（已有实测 10-40s） |
| 实例 | ★ 从实例断链 10 分钟 | 部分重同步 vs 全量重传选择、backlog 容量 |
| 实例 | 实例慢查询堆积（DEBUG SLEEP） | 探针不误杀、客户端超时熔断 |
| 网络 | ★ 主从分区（partition） | 脑屏防护（min-replicas-to-write）、双写检测 |
| 网络 | 跨 AZ 延迟 +100ms | 复制偏移增长、客户端读写分离降级 |
| 网络 | DNS 故障 | 集群发现缓存、静态拓扑兜底 |
| 资源 | ★ 内存压力（StressChaos） | maxmemory 驱逐策略生效顺序、热点保护 |
| 资源 | 磁盘写满（IOChaos/fs fill） | AOF 拒绝写 vs 优雅降级、告警时延 |
| 资源 | CPU 抢占（spot 回收） | Karpenter 预建节点 + 优雅排空（07.09.01 §5） |
| 时钟 | 节点时钟偏移 ±5s | 选举稳定性、证书校验、expire 精度 |
| 依赖 | 缓存客户端版本灰度故障 | 双客户端共存、快速回滚 |

## 5. 演练组织机制

- **演练日历**：每月一个主场景（与 自我验证修正机制 §3 月度轮换衔接），季度一次综合游戏日；提前 1 周公告窗口与中止条件。
- **游戏日（GameDay）**：跨团队（开发/SRE/DBA）按剧本注入真实故障，验证**人**的响应同样达标（自动恢复后是否有人跟进根因）。
- **分级晋级**：预发自动执行（纳入 CI）→ 生产只读类（无写影响）→ 生产写路径（窗口期 + 审批）。
- **结果归档**：每次演练回填 07.04.03 演练验证记录表 + 更新 runbook 缺口；失败场景必须转化为防护改造项（记入执行计划式跟踪）。

## 6. 性能分析：演练指标

- **恢复时间分布**：不只看均值，看 P95/P99——韧性是分布尾部的性质（与 05.06 延迟分布建模同源）。
- **稳态偏离积分**：故障期间稳态指标偏离的积分面积（比单点阈值更敏感于缓慢降级）。
- **演练覆盖度**：已演练场景数 / 风险登记册场景总数（目标 ≥80%）。
- **注入到检测时延**：$T_{detect}$ 的演练实测值对比告警规则的理论检测周期，反向校准告警阈值（太多误报 = 阈值松，漏检 = 阈值紧）。

## 7. 典型场景

1. **季度综合演练（金融）**：Chaos Mesh 编排"主实例宕机 + 跨 AZ 延迟 + 客户端洪峰"三连注入，验证 RTO 预算与熔断降级链路。
2. **发布前韧性门槛**：预发环境每次发版自动跑最小混沌套件（实例 kill + 分区），全过才允许生产发布。
3. **backlog 容量校准**：从实例断链场景实测"重连后走全量重传"的边界时间，反向确定 repl-backlog-size 生产值（替代拍脑袋）。
4. **新机房验收**：上架前全场景演练通过 = 验收门槛之一。
