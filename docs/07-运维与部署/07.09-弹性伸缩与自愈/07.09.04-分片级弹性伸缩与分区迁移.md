## 1. 概述：分片伸缩的独特性

Pod 层伸缩移动的是**无状态算力**（副本随便加减）；分片层伸缩移动的是**有状态数据**，三个独特性：

1. **数据有重量**：迁移时间 ∝ 数据量（[01.03.05](../../01-理论基础/01.03-分布式缓存算法/01.03.05-数据分片数学与再平衡模型.md) §3 成本模型），不能秒级完成。
2. **迁移有窗口**：目标加载完成前存在归属切换瞬间，客户端拓扑缓存需刷新（MOVED/ASK）。
3. **缩容不可逆性风险**：数据迁出后若剩余分片故障，恢复集缩小——缩容必须比扩容保守。

## 2. 主动与被动伸缩模型

### 2.1 模型定义

| 维度 | 被动伸缩（Reactive） | 主动伸缩（Predictive） |
| ---- | -------------------- | ---------------------- |
| 触发 | 水位/延迟越过阈值 | 流量预测（时序模型/日历） |
| 提前量 | 0（滞后于负载） | 预测 horizon $T_p$ |
| 适用 | 不可预测突发 | 周期性强（大促/日峰值） |
| 风险 | 扩容完成前可能击穿 | 预测偏低同样击穿；偏高浪费 |

### 2.2 决策边界（推导自延迟账，B 级）

分片伸缩总延迟 $T_{scale} = T_{detect} + T_{procure} + T_{migrate} + T_{warm}$（[07.09.01](./07.09.01-自动伸缩实践.md) §7 延迟账的分片版，其中 $T_{migrate}$ 占主导）。设负载从阈值的上升速率为 $r$（QPS/分钟，来自历史 metric），则被动伸缩期间负载超出安全水位的时间积分（"超限暴露量"）：

$$E_{exposure} \approx \frac{1}{2} \cdot r \cdot T_{scale}^2$$

当 $E_{exposure}$ 超过 miss 风暴/延迟违约的容忍预算时，必须引入主动伸缩把 $T_{detect}$ 提前到负载到来之前（日历触发）或用预测模型压低 $r$ 的有效值。**工程判据**：上升沿 $r$ 稳定可测（季节性强）→ 主动；突发主导 → 被动 + 限流兜底。

### 2.3 混合策略（生产惯例，C 级）

基线容量用主动伸缩维持（按预测曲线提前一天/数小时 reshard）；被动水位（内存 >70%、P99 > SLO×0.8）作为二道防线触发紧急扩容；限流降级作为三道。

## 3. reshard 机制与活性保障

### 3.1 标准流程

```text
1. 选目标节点（内存/CPU 水位最低的主节点）
2. redis-cli --cluster reshard <任意节点>
   → 指定迁出槽段、目标节点 ID、槽数、pipeline/阈值
3. 逐槽迁移：SETSLOT IMPORTING → 逐 key MIGRATE → SETSLOT NODE 广播
4. 校验：cluster check 全槽覆盖；各节点 keyspace 分布符合权重
```

### 3.2 活性保障要点

| 风险 | 保障机制 |
| ---- | -------- |
| 迁移中途客户端写入丢失 | ASK 重定向（迁移中 key）+ MOVED（归属变更后）；客户端必须实现 |
| 迁移与故障转移并发 | 槽位 epoch 仲裁，未决迁移的槽在转移后重新确认 |
| 大 key 阻塞 | MIGRATE 单 key 原子但大 key 传输阻塞源节点——大 key 先拆（[04.04.05](../../04-架构设计/04.04-缓存问题与治理/04.04.05-大Key问题.md)） |
| 迁移耗尽带宽 | pipeline 限流 + 业务低峰窗口 + 独立迁移网卡（K8s NetworkPolicy 隔离） |

## 4. 迁移期间的一致性窗口

逐 key 原子迁移 ≠ 全槽原子切换。窗口分析（Redis Cluster 规范，B 级）：

- **单 key**：MIGRATE 原子（DUMP+RESTORE+DEL 同事务），无窗口。
- **槽归属切换瞬间**：SETSLOT NODE 广播到全集群有传播时延（Gossip 周期），期间不同节点可能短暂持有不同归属视图 → 客户端 ASK/MOVED 重试收敛。
- **多 key 操作跨迁移**：同槽多 key 若在迁移中分散到两节点 → 命令拆分时结果非原子。应用层保证：迁移窗口内暂停该槽段的跨 key 事务，或以版本号兜底。

## 5. 自动化等级

| 等级 | 描述 | 数据面干预 | 适用 |
| ---- | ---- | ---------- | ---- |
| L0 人工 | DBA 手动 reshard | 全人工 | 变更极少的稳定集群 |
| L1 工具辅助 | 脚本生成 reshard 命令 + 前检清单 | 人工执行 | 中小集群 |
| L2 半自动 | 水位告警 → 一键审批 → operator 执行 reshard | 自动执行，人工审批 | 生产推荐起点 |
| L3 全自动 | 预测/水位驱动 operator 自主迁移（[cloud-native-cache](../../04-架构设计/04.03-行业应用场景/04.03.16-云原生缓存趋势与实践.md) 的 KubeBlocks/OT-CONTAINER-KIT 方向） | 全自动 + 审计 | 大规模平台 |

**保守性设计**：缩容统一 L2 起步（审批必备）；扩容可到 L3。

## 6. 性能分析：伸缩延迟账

以"3 主各 32GB、单槽 2GB、迁移带宽 100MB/s"为例（C 级估算）：

| 阶段 | 估算 | 主导因素 |
| ---- | ---- | -------- |
| 检测 | 1-5 min | 指标窗口 |
| 扩容节点就绪 | 5-10 min | 容器/云实例交付 |
| reshard 单槽 | ~20 s（2GB ÷ 100MB/s + 加载） | 带宽与 fork |
| 全量再均衡（每节点迁出 1/4 槽） | 8 槽 × 20s ≈ 3 min（并行下） | 并行度 |
| 预热（回填热点） | 与命中率恢复相关 | 预热策略（[04.04.09](../../04-架构设计/04.04-缓存问题与治理/04.04.09-缓存预热与冷启动治理.md)） |

**总账 ~10-20 分钟**——这就是为什么大促扩容必须提前（主动），以及为什么 L1 工具化值得投入。

## 7. 典型场景

1. **大促前主动扩容**：流量预测曲线提前 T_scale+余量触发 reshard；缩容排期到节后低峰。
2. **水位被动扩容**：内存倾斜度 S_data>2（[01.03.05](../../01-理论基础/01.03-分布式缓存算法/01.03.05-数据分片数学与再平衡模型.md) §4）且预测持续上涨 → L2 流程。
3. **节点替换（硬件/版本升级）**：逐个节点迁空 → 替换 → 迁回（滚动重平衡，全程不降低副本数）。
